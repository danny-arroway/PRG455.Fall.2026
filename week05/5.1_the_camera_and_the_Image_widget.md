### 1. Two Cameras, Two Display Paths

Every widget you've used so far — `M5Label`, `M5Button`, `M5Slider`,
`M5Bar`, `M5Switch` — is an **M5UI** object. It's a child of `page0`,
LVGL owns its pixels, and LVGL redraws it as part of the normal
`M5.update()` loop.

The camera breaks that pattern in one specific way. The CoreS3's
`camera` module hands you a raw frame — an `image.Image` object — once
per call to `camera.snapshot()`. There is no `M5Camera` widget that
continuously streams that frame into an LVGL object for you. To show a
**live** feed, you draw each captured frame directly onto the screen
with the lower-level display API:

```python
img = camera.snapshot()
M5.Lcd.show(img, 0, 0, 320, 240)
```

`M5.Lcd.show()` writes pixels straight to the display hardware. It does
**not** go through `page0`, and LVGL doesn't know it happened. This is
the same `M5.Lcd` you used briefly in Lecture 3 §3.4 for raw touch —
the layer *underneath* M5UI, not part of it.

`M5Image`, on the other hand, **is** an M5UI widget — but it only
displays a **file already saved to storage**, referenced by path:

```python
photo = m5ui.M5Image("/flash/photo.jpg", x=10, y=10, parent=page0)
```

There's no method on `M5Image` that takes a live frame directly. To get
a captured photo from the camera onto an `M5Image` widget, you have to
save it as a file first, then point the widget at that file with
`set_image()`.

**The consequence for your layout:** a live preview drawn with
`M5.Lcd.show()` ignores every M5UI widget's stacking and paints
straight over whatever is on screen at those coordinates, every frame.
If you put a button in the same rectangle you're drawing the preview
into, the button will be repeatedly painted over and become unusable.
This week's lab keeps the live preview and the UI controls in
**separate, non-overlapping regions** of the screen for exactly this
reason.

### 2. Initializing the Camera

```python
import camera

camera.init(pixformat=camera.RGB565, framesize=camera.QVGA)
```

Two things worth knowing before you touch this:

- **`pixformat` only supports `camera.RGB565`** on the CoreS3 — there's
  no JPEG-native capture mode to select at init time. You always
  capture RGB565 and convert to JPEG afterward, in software, only when
  you actually want to save a file.
- **`framesize` controls the raw frame's resolution**, not what you
  display it at. `camera.QVGA` (320×240) exactly matches the CoreS3's
  screen, which is why this lecture uses it — no scaling required. You
  could initialize at a smaller size like `camera.QQVGA` (160×120) if
  you wanted a smaller preview area, but you'd need to size your
  `M5.Lcd.show()` rectangle to match, or the image will only occupy
  part of the region and leave stale pixels around it.

Call `camera.init()` once, in `setup()`, after `M5.begin()` — the same
place you initialized the IMU in Lecture 4.

### 3. Live Preview in `loop()`

```python
def loop():
    M5.update()
    frame = camera.snapshot()
    M5.Lcd.show(frame, 0, 40, 320, 200)
```

`camera.snapshot()` returns a new `image.Image` every call — you don't
need to store it across iterations, and there's nothing to release or
free in MicroPython's memory model here.

`M5.Lcd.show(img, x, y, w, h)` draws it at that rectangle. In this
example, the top 40 pixels of the 240px-tall screen are left clear for
a title and button row, and the preview fills the remaining
320×200 region below it — a layout you'll reuse directly in the lab.

Every widget event you registered in earlier weeks — button presses,
switch toggles — still fires normally during this loop, because
`M5.update()` is still being called every iteration exactly as before.
The camera doesn't change your event-handling code at all; it just
adds a second thing happening inside `loop()`, alongside the UI pump.

### 4. Capturing and Saving a Photo

A **Capture** button follows the exact same handler shape you've used
since Lecture 3 — `add_event_cb`, dispatch on `event_struct.code` — the
new part is what happens inside the handler:

```python
import jpg

def capture_button_clicked(event_struct):
    try:
        frame = camera.snapshot()
        jpg_img = jpg.encode(frame, 80)
        with open("/flash/photo.jpg", "wb") as f:
            f.write(jpg_img.bytearray())
        result_image.set_image("/flash/photo.jpg")
        status_label.set_text("Captured")
    except Exception as e:
        print("Capture failed:", e)
        status_label.set_text("Capture failed -- see console")


def capture_button_handler(event_struct):
    if event_struct.code == lv.EVENT.CLICKED:
        capture_button_clicked(event_struct)
    return
```

Four things happen inside the `try` block, in order, every time the
button is pressed:

1. **Grab one frame** with `camera.snapshot()` — the same call the
   preview loop is already making. This returns an `image.Image` in
   RGB565 format.
2. **Encode it to JPEG** with `jpg.encode(frame, 80)` — a
   function from the CoreS3-only `jpg` module, imported separately.
   The second argument is quality, roughly 0–100; higher keeps more
   detail but produces a larger file. 80 is a reasonable default for a
   small on-device photo — there's no need to tune this precisely for
   the lab. **`jpg.encode()` does not return raw bytes** — it returns
   another `image.Image`, just tagged with a JPEG format instead of
   RGB565. There is no `.to_jpeg()` method on `image.Image` itself;
   encoding always goes through the standalone `jpg` module.
3. **Extract the actual byte data** from that returned image with
   `.bytearray()` — this is the step that gets you something
   `write()` can actually put in a file.
4. **Write those bytes to flash in binary mode**, then tell
   `result_image` (an `M5Image` widget already created in `setup()`)
   to load that file with `set_image()`.

**Why `"wb"`, not `"w"`?** `jpg_img.bytearray()` returns binary data —
a `bytearray`, not a `str`. Opening the file in text mode (`"w"`) and
handing it bytes-like data is exactly the kind of thing that looks
reasonable and can appear in example code, but is a **type mismatch**
that may raise inside the handler on real hardware, depending on your
exact firmware build. `"wb"` (write-binary) is the correct mode any
time you're writing the output of `jpg.encode()` — this is the same
`"rb"`/`"wb"` distinction you'd apply for any binary file, not just
images.

**Why `jpg.encode(frame, 80)` and not `jpg.encode(frame, quality=80)`?**
M5Stack's own reference documentation shows `quality` as a named
keyword argument. On the CoreS3's actual UIFlow2 firmware,
`jpg.encode()` is implemented as a native (C-level) function, and
native functions in this MicroPython build frequently **do not accept
keyword arguments at all**, even when the published signature suggests
they should. Calling it with `quality=80` raises:

```
TypeError: function doesn't take keyword arguments
```

Pass the quality value **positionally** instead: `jpg.encode(frame,
80)`. This is a firmware/documentation mismatch, not a mistake in your
code — the same category of gap as the `M5Bar` font quirks and the
`get_state()` lag from earlier weeks. When a documented keyword
argument raises this exact error, positional-only is the fix to try
first, on this firmware, for any native module function — not just
`jpg.encode()`.

**Why wrap the whole thing in `try`/`except`?** Because a widget event
handler runs inside M5UI's own event dispatch, not inside your
program's top-level `while True:` loop — an exception raised in here
does **not** reliably propagate up to the `try`/`except` around
`setup()`/`loop()` at the bottom of the file. Without a local
`try`/`except`, a failure in `capture_button_clicked()` can fail
**silently**: the button appears to do nothing, no traceback prints
anywhere, and the only symptom is that `/flash/photo.jpg` never
appears. Printing the exception yourself, right where it happens, is
the only reliable way to see what actually went wrong. Keep this
pattern for **any** event handler that does file I/O, network calls,
or anything else that can fail for reasons outside your control.

**Why not skip the file and hand `M5Image` the frame directly?**
Because `M5Image`'s constructor and `set_image()` both take a **file
path string**, not an `image.Image` object or a raw byte buffer —
that's the API, not a workaround. Saving to flash first isn't extra
credit-seeking complexity; it's the only path `M5Image` actually
accepts.

**A naming trap to watch for:** the module is `jpg`, and its function
is `jpg.encode()` — not `image.to_jpeg()`, `camera.to_jpeg()`, or
anything hung off the frame object itself. If you ask an AI tool to
help with this step, it may confidently suggest `.to_jpeg()` because
that method name is common on other camera/image libraries (OpenMV,
several desktop Python imaging packages) — it does not exist on this
firmware's `image.Image` class, and calling it raises
`AttributeError: 'Image' object has no attribute 'to_jpeg'` on the
physical device. This is exactly the kind of plausible-but-wrong AI
output the course's AI Collaboration Policy asks you to catch by
testing on real hardware before trusting the code — and the silent
failure mode above is exactly *why* testing on hardware matters more
than reading the code and assuming it's correct.

### 4.1 Verifying a Capture Actually Happened

Because Capture writes to flash rather than showing an immediate
visible result the way a label update does, it's worth knowing how to
check your work independently of trusting the UI:

```python
import os
print(os.listdir("/flash"))
print(os.stat("/flash/photo.jpg"))
```

Run this from the WebTerminal, or as a quick standalone Run Once
script, after pressing Capture. `os.listdir("/flash")` should include
your photo's filename, and `os.stat()` should return without raising —
if it raises `OSError: [Errno 2] ENOENT`, the file was never written,
which means the handler either didn't run or failed before reaching
the `open()` call. That's your cue to add the `try`/`except`-with-print
pattern from §4 if you haven't already, rather than staring at the
code trying to spot the bug by inspection.

This is a useful general habit, not just a one-time troubleshooting
step: **a widget updating on screen is not proof that a file operation
underneath it succeeded.** `result_image.set_image()` will happily keep
showing the *previous* successfully-loaded image if `set_image()` is
never reached at all — nothing about the screen looking normal tells
you the write behind it worked.

### 5. `M5Image` — API Surface You'll Actually Use

`M5Image` has a narrower method set than the widgets from earlier
weeks — there's no `get_value()`, no `VALUE_CHANGED` event, because a
photo doesn't have "state" the way a slider position does. What you
have:

```python
result_image = m5ui.M5Image(
    "/flash/res/img/uiflow.jpg",   # path — must be a real file at creation time
    x=10, y=40,
    parent=page0,
)

result_image.set_image("/flash/photo.jpg")   # swap to a different file
result_image.set_pos(10, 40)                  # reposition
result_image.set_rotation(90)                 # rotate 0/90/180/270 degrees
result_image.set_scale(1.5, 1.5)              # scale x, y independently
```

**A gotcha specific to this widget:** `M5Image`'s constructor requires
a **path that already exists** at the moment you create the widget —
you can't hand it an empty string or a path to a file that doesn't
exist yet and expect it to render blank and wait. This week's lab
ships a small placeholder image in the starter files for exactly this
reason: create the widget pointed at the placeholder in `setup()`, then
swap it to the real captured photo with `set_image()` once one exists.
Attempting to construct `M5Image` with a nonexistent path is a crash at
widget-creation time, not a silent no-op — the same failure shape as
the missing-font crash from Lecture 3 §3.1.

Unlike `M5Label`, `M5Image` **does** have implicit sizing from the
image file itself — it draws at the source image's native pixel
dimensions. There's no `w`/`h` constructor argument to stretch it; if
you need a specific display size, use `set_scale()` to scale up or down
from the source resolution, not a box parameter.

### 6. Full Worked Example — Live Preview + Capture + Redisplay

This mirrors the shape you'll build in Lab 5: a title bar, a live
camera preview filling most of the screen, and a Capture button that
saves a photo and swaps a small `M5Image` thumbnail to show it —
without the live preview and the thumbnail fighting over the same
pixels.

```python
# SPDX-License-Identifier: MIT
#
# PRG455 Lecture 5 -- Live Preview + Capture + Redisplay
# Demonstrates M5.Lcd.show() for live camera frames and M5Image for a
# saved photo, kept in separate, non-overlapping screen regions.

import os, sys, io
import M5
from M5 import *
import m5ui
import lvgl as lv
import camera
import jpg

ANIM_OFF = getattr(lv, "ANIM_OFF", 0)

page0 = None
title_label = None
capture_button = None
result_image = None
status_label = None

PHOTO_PATH = "/flash/photo.jpg"
PLACEHOLDER_PATH = "/flash/res/img/uiflow.jpg"  # ships with firmware


def capture_button_clicked(event_struct):
    try:
        frame = camera.snapshot()
        jpg_img = jpg.encode(frame, 80)
        with open(PHOTO_PATH, "wb") as f:
            f.write(jpg_img.bytearray())
        result_image.set_image(PHOTO_PATH)
        status_label.set_text("Captured")
    except Exception as e:
        print("Capture failed:", e)
        status_label.set_text("Capture failed -- see console")


def capture_button_handler(event_struct):
    if event_struct.code == lv.EVENT.CLICKED:
        capture_button_clicked(event_struct)
    return


def setup():
    global page0, title_label, capture_button, result_image, status_label

    M5.begin()
    Widgets.setRotation(1)
    m5ui.init()
    page0 = m5ui.M5Page(bg_c=0xFFFFFF)

    camera.init(pixformat=camera.RGB565, framesize=camera.QVGA)

    title_font = getattr(lv, "font_montserrat_20", lv.font_montserrat_14)
    title_label = m5ui.M5Label(
        "Lecture 5 -- Camera", x=10, y=4,
        text_c=0x000000, bg_c=0xFFFFFF, bg_opa=0,
        font=title_font, parent=page0,
    )

    capture_button = m5ui.M5Button(
        text="Capture", x=180, y=4, w=100, h=28,
        bg_c=0x2196F3, text_c=0xFFFFFF,
        font=lv.font_montserrat_14, parent=page0,
    )
    capture_button.add_event_cb(capture_button_handler, lv.EVENT.ALL, None)

    # Thumbnail sits in the top-right corner, clear of the live preview
    # region drawn each loop() below -- see Section 1.
    result_image = m5ui.M5Image(
        PLACEHOLDER_PATH, x=290, y=4, parent=page0,
    )
    result_image.set_scale(0.15, 0.15)

    status_label = m5ui.M5Label(
        "", x=10, y=210,
        text_c=0x000000, bg_c=0xFFFFFF, bg_opa=0,
        font=lv.font_montserrat_14, parent=page0,
    )

    page0.screen_load()


def loop():
    M5.update()
    frame = camera.snapshot()
    M5.Lcd.show(frame, 0, 40, 320, 165)


if __name__ == '__main__':
    try:
        setup()
        while True:
            loop()
    except (Exception, KeyboardInterrupt) as e:
        try:
            m5ui.deinit()
            from utility import print_error_msg
            print_error_msg(e)
        except ImportError:
            print("please update to latest firmware")
```

Walk through why each region is where it is:

- **Title and Capture button** occupy `y=4` to about `y=32` — well
  clear of the preview.
- **Live preview** is drawn at `y=40` to `y=205` (`h=165`), leaving a
  gap before the bottom.
- **Status label** sits at `y=210`, below the preview, so it isn't
  painted over every frame the way something inside the preview
  rectangle would be.
- **The thumbnail `M5Image`** is placed at `x=290`, off to the right,
  outside the preview's `x=0` to `x=320` — wait, that's actually
  *inside* the preview's horizontal span. Look closely at the `y`
  values instead: the thumbnail sits at `y=4`, entirely above the
  preview's `y=40` start, so the two regions don't overlap even though
  their horizontal ranges do. This is the kind of two-dimensional
  overlap check you'll need to do yourself when you lay out Lab 5 — it
  isn't enough to check `x` or `y` alone.

### 7. Key Takeaways

- Live video goes through `M5.Lcd.show(img, x, y, w, h)` — the raw
  display layer, not M5UI. `M5Image` cannot stream live frames.
- `camera.init()` only accepts `camera.RGB565` for `pixformat`; convert
  to JPEG only when you need a file, using the separate `jpg` module's
  `jpg.encode(frame, quality)` — **not** a `.to_jpeg()` method, which
  doesn't exist on this firmware's `image.Image` class. `jpg.encode()`
  returns another `image.Image`; call `.bytearray()` on that to get
  the actual bytes to write.
- **Pass `jpg.encode()`'s quality argument positionally**
  (`jpg.encode(frame, 80)`), not as a keyword (`quality=80`) — despite
  the published docs showing it as a keyword argument, this firmware's
  native binding raises `TypeError: function doesn't take keyword
  arguments` if you do. Positional-only is a common gap between
  documented and actual behaviour for native module functions on this
  firmware.
- **Open the file in binary mode (`"wb"`), not text mode (`"w"`),**
  whenever you're writing the output of `jpg.encode().bytearray()` —
  it's binary data, and text mode is a type mismatch waiting to fail.
- **Wrap event-handler bodies that do file I/O in their own
  `try`/`except`** and print the exception. A failure inside a widget
  event handler does not reliably reach the `try`/`except` around
  `setup()`/`loop()`, so without a local handler, a broken Capture
  button fails silently — nothing crashes, nothing prints, the file
  simply never appears.
- `M5Image` displays **files**, not frame objects — save the JPEG to
  flash, then call `set_image()` with that path.
- `M5Image` must be constructed with a path that already exists;
  point it at a placeholder file in `setup()` if the real photo doesn't
  exist yet.
- Because the live preview paints over raw screen coordinates every
  frame, ignoring LVGL's widget stacking, you must keep it in a
  rectangle that never overlaps any other widget — check both `x` and
  `y` ranges, not just one.
- **A widget updating normally is not proof that the file operation
  behind it worked** — verify a capture actually landed on flash with
  `os.listdir()` / `os.stat()` (§4.1) rather than trusting the screen
  alone.
