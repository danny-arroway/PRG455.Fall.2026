# PRG455 — Week 2: Precision Prompting and Context Economy

**Reading for Week 2 · Read before your Week 3 lab**

Next week you start generating Python code that will run on your Core S3 and on your PC. This
reading is about how to ask for that code so you get something correct, and so you do not run out
of your Claude Pro allowance halfway through a lab period.

Both of those problems have the same cause and the same fix.

---

## 1. Two things that will go wrong if you skip this

### You will run out of allowance

Your Pro subscription runs on a **rolling five-hour window plus a weekly cap**, and that
allowance is shared across claude.ai in your browser, Claude Desktop, and Claude Code in VS Code
or the terminal. They all draw from one pool.

Working the way most people naturally work — one long sprawling conversation, whole files pasted
over and over, vague requests, correcting by saying "no, try again" — can burn a five-hour window
in about forty minutes. Then you are sitting in lab unable to do anything until it resets.

### You will get code that runs and is wrong

This is the more serious one.

You have spent three semesters writing C. In C, when you are unclear, the compiler stops and
tells you. That is not what happens here:

> **A compiler that does not understand you stops and tells you.**
> **A language model that does not understand you produces something anyway.**

An ambiguous request does not produce an error message. It produces confident, well-formatted,
plausible-looking code that answers a question you did not ask. On screen that is annoying. Wired
to a microcontroller, it is a defect you will chase for an hour before realising the code was
never doing what you thought.

**Correct-looking and correct are different properties.** Only one of them survives contact with
a serial port.

---

## 2. The mechanic that explains everything else

Here is the single fact that makes the rest of this reading obvious rather than arbitrary:

> **A language model has no memory between messages. It is stateless.**
>
> Every time you press Enter, your entire conversation — every message you sent, every reply you
> received, every file you attached — is sent again, from the beginning.

Picture it:

```
Turn 1:  [your Q1]                                    → small
Turn 2:  [Q1] [A1] [your Q2]                          → bigger
Turn 3:  [Q1] [A1] [Q2] [A2] [your Q3]                → bigger still
Turn 4:  [Q1] [A1] [Q2] [A2] [Q3] [A3] [your Q4]      → ...
```

Two consequences follow immediately.

**The twentieth message in a conversation costs many times what the first one did**, even if you
only typed three words.

**A file you paste is not pasted once.** Paste a 400-line file at turn 3, then have twenty more
turns, and that file was transmitted eighteen more times. You paid for it every single time.

### Tokens, roughly

Tokens are the units being counted. You do not need precision, just an instinct for scale:

| | Rough size |
|---|---|
| Plain English | ~4 characters per token |
| Python source code | denser — punctuation and indentation all cost |
| One page of text | ~500–800 tokens |
| A 200-line Python file | very roughly 2,000–3,000 tokens |

The instinct to develop: **a file is expensive, a sentence is cheap.** A well-chosen sentence
beats a pasted file almost every time.

### Why long conversations also get *worse*

Cost is not the only problem. Quality degrades too.

In a conversation containing six abandoned attempts, three changes of direction, and a pasted
file that is now four versions out of date, the model is trying to satisfy all of it. Contradictory
context produces hedged, confused, or regressive output — code that re-introduces a bug you fixed
twenty turns ago.

> **A long conversation is not a rich conversation. It is a noisy one.**

When you hear someone say "Claude was working well and then got worse," this is almost always
what happened. It is not the model. It is a conversation that has accumulated too much
contradictory history.

## 3. Precision is the efficiency strategy

Students usually assume detailed prompts waste tokens. The opposite is true, and it is worth
seeing why.

### A worked example

Suppose you want a program to read temperature from your Core S3.

**The vague version:**

```
write a python program to read temperature from my esp32
```

Before reading on, count what the model has to guess:

| It must invent | It might pick |
|---|---|
| Which side is this code for? | Your PC, or the microcontroller — completely different programs |
| How is the data transmitted? | Serial, Wi-Fi, MQTT, Bluetooth |
| What is the data format? | Raw number, CSV, JSON, key=value |
| Which port, which baud rate? | Anything |
| Is there a GUI? | Console script, or Tkinter |
| One reading, or continuous? | Either |
| What happens if the device is absent? | Crash, silence, retry |
| Which sensor, what units? | Anything |

That is eight guesses. Even if each one is individually reasonable, the combination is almost
certainly not what you needed.

**The specified version:**

```
Write a Python 3.14 program that runs on my PC (Windows) and reads temperature
readings sent from an M5Stack Core S3 over USB serial.

The device sends one line per second in this exact format:
    TEMP,<sequence>,<celsius>
for example:
    TEMP,42,23.75

Requirements:
- Use pyserial. Port is COM5, 115200 baud.
- Print the sequence number and temperature to the console.
- If a line is malformed, print a warning and continue — do not crash.
- If the device is unplugged, print a message and keep trying to reconnect.
- Standard library plus pyserial only. Single file. No GUI yet.
```

### The arithmetic

The second prompt uses more tokens **on that one turn**. But the first prompt buys you four
rounds of correction — and every round resends the entire conversation, including the wrong code
and your complaints about it.

**Total cost of the vague prompt is far higher.** Precision is not the opposite of efficiency. It
is how you achieve it.

---

## 4. The three ambiguities that bite in this course

Most bad generations in PRG455 trace to one of these three. Check every prompt against them.

### 1. Which machine is this code for?

The most common failure in this course, by a wide margin.

Your Core S3 runs **MicroPython**, with the `M5` and `machine` libraries, and **no `tkinter`**.
Your laptop runs **CPython**, with `tkinter` and `pyserial`, and **no `machine`**. Code written
for one is nonsense on the other.

**Say which side. Every time.** "Device-side MicroPython" or "PC-side Python" costs you four
words and eliminates the single largest source of wasted time in this course.

### 2. What exactly is on the wire?

"Send sensor data" is not a specification. All four of these are valid, and all four need
different parsers:

```
23.75
TEMP,23.75
{"temp": 23.75}
t=23.75\r\n
```

If you do not specify the format, you get one at random. Worse — if you generate the device code
and the PC code in separate conversations without specifying the format in both, **the two halves
of your own system will disagree with each other**, and the bug will look like a hardware fault.

### 3. What should happen when it goes wrong?

Unspecified failure behaviour is where hardware projects die.

What happens on: unplug mid-stream, a malformed line, a timeout, a partial line with no newline,
the device resetting during transmission?

If you do not say, you get code that quietly assumes nothing ever fails. That code passes in the
lab and fails in the demo — and failure handling is explicitly graded in this course.

## 5. The four-part prompt pattern

Use this structure for every code request this term.

```
1. CONTEXT      Which machine? Which Python? Which libraries?
                What already exists?

2. TASK         What you want. One or two sentences.

3. CONSTRAINTS  What it must use. What it must NOT do.
                Exact data format. Sample rate. Units.
                Failure behaviour.

4. ACCEPTANCE   How you will know it worked.
```

- Missing **context** gets you code for the wrong machine.
- Missing **constraints** gets you `time.sleep()` and a frozen window.
- Missing **acceptance** means you cannot tell whether you succeeded.

### A complete example

```
CONTEXT
I am writing MicroPython for an M5Stack Core S3 running UIFlow2 v2.5.0.
The M5 library is available. This code runs on the device, not on my PC.

TASK
Read the built-in IMU accelerometer and send the readings to my PC over USB serial.

CONSTRAINTS
- Sample at 10 Hz.
- Output one line per sample, format: ACC,<seq>,<x>,<y>,<z>
- Three decimal places on each axis.
- Sequence number starts at 0 and increments.
- Use time.sleep_ms(), not time.sleep().
- Must call M5.update() each loop iteration.
- No Wi-Fi, no networking.

ACCEPTANCE
- Running `mpremote run imu.py` prints ten lines per second.
- Tilting the device changes the values.
- One axis reads near 1.0 when pointing down.
- The program can be interrupted with Ctrl+C.
```

### Notice what just happened

Writing that prompt required you to decide the sample rate, the data format, the precision, and
the failure behaviour. **That is the engineering.** The code generation is the cheap part.

This is also, not coincidentally, exactly what your labs are graded on. The specification you
write for Claude is the specification your instructor reads.

## 6. Correcting without burning your allowance

When the first attempt is not right, how you respond determines whether the fix costs you a
little or a lot.

| ❌ Vague and expensive | ✅ Precise and cheap |
|---|---|
| "that didn't work" | "Line 14 raises `AttributeError: 'module' object has no attribute 'Imu'`. Here is `dir(M5)` output: [...]. Which is the correct accessor?" |
| "can you fix it" | "The sequence number resets to 0 after every read. Fix only that; leave everything else unchanged." |
| "make it better" | "Change the sample rate from 10 Hz to 5 Hz. Show only the changed lines." |
| "it's still broken" | "After your change I get [exact error]. Here are the 6 relevant lines: [...]" |

Three habits worth building:

**Always paste the exact error text.** Never paraphrase an error. The text *is* the diagnosis —
"it says something about an attribute" throws away the information that would have solved it.

**Ask for only the changed lines.** Once a file is more than fifty lines or so, "show only the
modified function" saves a great deal on every subsequent turn.

**Restate the constraint that was violated.** Models drift back toward common patterns. If
`after()` instead of `sleep()` mattered the first time, say it again in the correction.

## 7. Five habits for context economy

In priority order:

**1. One task, one conversation.**
Finish the serial reader, then start a *new* conversation for the GUI. Do not run one
conversation all evening — you are paying for the whole history on every message.

**2. Use `/clear` between unrelated tasks in Claude Code.**
One command. Resets the accumulated cost.

**3. Paste the function, not the file.**
If the bug is in `on_button_click`, send `on_button_click`. Code irrelevant to your question does
not just cost tokens — it makes the answer worse.

**4. After two failed corrections, restart.**
This is the one people resist and the one that saves the most. Arguing with a bad generation is
the most expensive thing you can do, because every round drags the entire failed history forward.
Open a new conversation, write a better specification using what you just learned, and start
clean.

**5. Put permanent constraints in a file.**
See the next section.

## 8. `CONTEXT.md` — the highest-leverage habit

Some constraints apply to *everything* you write this term. Restating them in every prompt is
wasteful and you will forget half of them half the time. Write them once instead.

Create a file in your repository:

```markdown
# PRG455 project constraints

## PC-side code
Python 3.14, Windows. Standard library plus pyserial only.
Tkinter for GUI. No third-party GUI frameworks.
Never block the Tkinter event loop — use after(), never time.sleep().

## Device-side code
MicroPython on M5Stack Core S3, UIFlow2 v2.5.0.
M5 library available. Call M5.update() every loop iteration.
Use time.sleep_ms(). No Wi-Fi unless the lab asks for it.

## Wire protocol
Comma-delimited ASCII lines, terminated with \n.
Format: <TAG>,<sequence>,<value>[,<value>...]

## Style
Comment the structure, not the syntax. I am a C programmer learning Python.
Explain any idiom beyond basic loops, functions, and classes.
```

That file is roughly 150 tokens. Restating all of it in every message would cost the same 150
tokens *per message* — and you would forget things.

**More importantly:** this is not extra work you are doing for the AI. It is the engineering
specification for your project. Your instructor reads it as your design documentation. You are
doing the work either way; this way it also improves everything Claude generates for you.

## 9. Which tool for which job

| Surface | Best for | Watch out for |
|---|---|---|
| **claude.ai chat** | Concepts, explanations, one-file drafts, "what does this error mean" | You paste files by hand, so it is easy to paste far more than needed |
| **Claude Code** (terminal or VS Code) | Working in a real repository, multi-file edits, reviewing diffs | It reads files to do its job — a sprawling session gets expensive fast |
| **`CONTEXT.md`** | Constraints that apply to every conversation | Keep it short; it is resent constantly |

Check `/status` in Claude Code before you start a lab. Knowing you have limited allowance left
before you begin is very different from discovering it at 8:40 on a Wednesday.

## 10. If you are not sure what to specify

A reasonable objection: *how can I write a precise prompt about something I do not understand
yet?*

Answer: ask a **question** first. Questions are cheap. Specifications come second.

```
What are the standard approaches for reading serial data in Python
without freezing a Tkinter GUI? Give me two or three options with
the trade-offs. No code yet.
```

That costs very little and tells you which constraints you need to state. Then write the
specification.

**Separating "help me understand this" from "write me this code" is itself a skill.** Mixing them
produces conversations that are long, expensive, and muddled.

## More before-and-after examples

### Reading a button on the Core S3

❌ `how do I read a button`

✅
```
MicroPython on M5Stack Core S3, UIFlow2 v2.5.0, M5 library available.
Device-side code, not PC-side.

Detect when Button A is pressed and print BTN,A,<count> over serial,
where count increments per press.

Constraints:
- Call M5.update() every loop iteration.
- Detect the press edge only — one line per press, not one per loop.
- Use time.sleep_ms(50) for debounce.
- No Wi-Fi.

Acceptance: pressing the button five times prints exactly five lines,
counting 1 to 5.
```

### Fixing a frozen GUI

❌ `my gui freezes help`

✅
```
Python 3.14 Tkinter on Windows. My GUI freezes for 5 seconds when I click Start.

Here is the callback:

def on_start(self):
    for i in range(5):
        self.label.config(text=str(i))
        time.sleep(1)

I believe the problem is that time.sleep() blocks the event loop.
Rewrite this using after() so the window stays responsive.
Change only this method; do not restructure the class.
```

### Parsing incoming serial data

❌ `parse the data from my esp32`

✅
```
PC-side Python 3.14, pyserial, Windows, COM5 at 115200.

The Core S3 sends lines like:  ACC,17,0.012,-0.998,0.043
Fields: tag, sequence number, then x, y, z as floats.

Write a function parse_line(line) that returns a dict with keys
seq, x, y, z — or returns None if the line is malformed.

Malformed cases to handle: empty line, wrong field count,
non-numeric field, missing tag, partial line with no newline.
Must never raise.

Acceptance: I will call it with each of those five malformed cases
and expect None each time, with no exception.
```

## Common questions

**Isn't a long detailed prompt using more tokens than a short one?**
On that one turn, yes. Over the whole task, no — and the whole task is what your allowance
measures. A short prompt buys four correction rounds, each one resending everything that came
before.

**Why not just paste my whole file every time? It's easier.**
Because you pay for it on every turn thereafter, and because code irrelevant to your question
makes the answer worse, not better. Send the function.

**Claude was working well and then got worse. Why?**
Almost always conversation length. Abandoned attempts and changes of direction are all still in
context, and the model is trying to honour all of them at once. Start fresh with a clean
specification.

**Can I just tell it to remember my constraints?**
There is no memory between conversations. That is exactly what `CONTEXT.md` solves.

**What if I run out of allowance mid-lab?**
Every lab in this course is designed so that once your code exists, you can finish without
generating anything further. Running out is a planning problem, not grounds for an extension —
which is why `/status` before you start matters.
