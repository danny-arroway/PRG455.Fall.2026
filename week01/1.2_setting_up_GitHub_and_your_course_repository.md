# PRG455 — Setting Up GitHub and Your Course Repository

**Week 1 · Student handout · Complete before your Week 2 lab**

Everything you produce in this course — every lab, every lab test, every project, and every
answer you get from Claude — lives in one repository on GitHub. This handout takes you from
having no GitHub account to having a published repository with the full course directory
structure in it.

Work through it in order. Do not skip the verification steps.

**Estimated time:** 45–60 minutes.

---

## Part 0 — What you are setting up, and why

**Git** is a version control system. It records snapshots of a folder over time, so you can see
exactly what changed, when, and why — and go back if you break something.

**GitHub** is a website that stores a copy of that folder in the cloud so it survives a dead
laptop and so your instructor can see it.

**GitHub Desktop** is a graphical application that drives Git without you having to learn Git
commands. That is what we will use in this course.

Why this matters here specifically: in this course you are required to commit **Claude's
generated answer before you modify it**. The difference between those two commits is the
evidence that you understood the code. Without version control, that evidence does not exist,
and a large part of your lab mark is unmarkable.

## Part 1 — Create a GitHub account (15 min)

> ### ⚠️ Two course requirements before you begin
>
> **1. You must register your GitHub account with a Gmail address.** Not your Seneca address,
> not Outlook, not Yahoo, not iCloud. A Gmail address is required so that account recovery,

>
> Both requirements are checked at sign-off. A repository created with the wrong email or left
> public will have to be redone.

### Step 1.1 — Choose a username before you start

Your GitHub username becomes a public web address: `github.com/yourusername`. Employers look at
it. Co-op interviewers look at it.

- **Good:** `jsmith-dev`, `j-smith`, `jamiesmith`, `jsmith2026`
- **Poor:** `xXgamerkingXx`, `hotgirl99`, `seneca_student_1`

You can change it later, but every link you have shared breaks when you do. Choose once.

### Step 1.2 — Sign up

1. Go to **github.com** in a browser.
2. Click **Sign up**.
3. **Enter your Gmail address.** This is a course requirement, not a suggestion.
   - Do **not** use your Seneca address. You lose access to institutional email after you
     graduate, and account recovery goes through email.
   - Do **not** use Outlook, Hotmail, Yahoo, iCloud, or a family domain. Collaborator
     invitations and notifications from GitHub are matched to the email on the account, and
     this course standardises on Gmail so that process is predictable for everyone.
   - If you do not already have one, open a second tab, go to **gmail.com**, and create an
     account before continuing. Choose an address you would put on a résumé.
   - **Write down which Gmail address you used.** You will need to give it to your instructor,
     and it must match the account that receives the collaborator invitation in Part 4.
4. Create a password. Use your password manager. If you do not have one, this is a good week to
   start.
5. Enter the username you chose in Step 1.1.
6. Complete the puzzle verification.
7. GitHub emails you an eight-digit code. Enter it.

### Step 1.3 — Set up two-factor authentication

GitHub requires two-factor authentication (2FA) on all accounts. You will be prompted to
configure it, either immediately or within a grace period. Do it now rather than being locked
out mid-term.

1. When prompted, choose **authenticator app** (Google Authenticator, Microsoft Authenticator,
   Authy, or the one built into your password manager).
2. Scan the QR code with the app.
3. Enter the six-digit code the app displays.
4. **GitHub then shows you recovery codes. Save them.** Screenshot them, save them to a file
   somewhere that is not your laptop, or print them. If you lose your phone and have no
   recovery codes, nobody — not GitHub, not your instructor — can recover the account, and you
   will be rebuilding your repository from scratch.

### Verification 1

Open `github.com` in a private/incognito window and log in with your username and password. You
should be asked for a 2FA code. If you are, the account is set up correctly.

Then confirm the email on the account: **Settings → Emails**. The primary address must be your
Gmail address. If it is not, add the Gmail address there, verify it, and set it as primary.

## Part 2 — Install GitHub Desktop (10 min)

### Step 2.1 — Download and install

1. Go to **desktop.github.com**.
2. Download the version for your operating system.
   - **Windows:** run the `.exe`. It installs without prompting for much.
   - **macOS:** open the `.zip`, then drag **GitHub Desktop** into your **Applications** folder.
     Launch it from Applications, not from the Downloads folder.
3. Launch GitHub Desktop.

### Step 2.2 — Sign in

1. On the welcome screen, click **Sign in to GitHub.com**.
2. Your browser opens. Authorise the application. You will be asked for your 2FA code.
3. Return to GitHub Desktop when the browser says you can close the tab.

### Step 2.3 — Configure your identity

GitHub Desktop asks for a name and email to stamp on your commits.

- **Name:** your real name, as it appears on your Seneca record. Your instructor has to match
  commits to a student in a class list.
- **Email:** GitHub offers a private, no-reply address (something like
  `12345678+username@users.noreply.github.com`). **Use it.** Otherwise your personal email
  address is embedded in every commit and is publicly searchable forever.

Click **Finish**.

### Verification 2

`File → Options` (Windows) or `GitHub Desktop → Settings` (macOS) → **Accounts** should show
your username. → **Git** should show your name and the no-reply email.

## Part 3 — Choose where your repository will live (5 min)

**Before you create anything, read this section. Getting it wrong causes problems that are
tedious to undo.**

Create a folder for this course somewhere sensible:

- **Windows:** `C:\Users\<you>\Documents\Seneca\`
- **macOS:** `/Users/<you>/Documents/Seneca/`

**Do not put your repository inside OneDrive, iCloud Drive, Google Drive, or Dropbox.** These
services sync files continuously, and Git also writes to files continuously. They fight, and
the result is a corrupted repository — often noticed for the first time on a due date. GitHub
is already your backup. You do not need a second one.

Also avoid folder names containing spaces or accented characters anywhere in the path. Some
tools you will use later in this course handle them poorly.

## Part 5 — Build the directory structure (15 min)

Your repository needs one folder per piece of assessed work:

```
PRG455.263/
├── README.md
├── .gitignore
├── lab1/
├── lab2/
├── lab3/
├── lab4/
├── lab5/
├── lab6/
├── lab7/
├── lab8/
├── labTest1/
├── labTest2/
├── project1/
└── project2/
```

**Spelling and capitalisation matter.** `labTest1` has a lowercase `l` and a capital `T`. Git
records the exact case, but Windows and macOS filesystems do not distinguish case, which makes
fixing a capitalisation mistake later unexpectedly awkward. Get it right the first time.

### The problem you are about to hit

**Git does not track empty folders.** If you create the eleven folders and switch to GitHub
Desktop, it will show *no changes to commit* and nothing will be uploaded. This confuses
everyone the first time.

The fix is to put a file in each folder. We will put a `README.md` in each one, which is useful
anyway — it is where you will describe what that piece of work does.

Use **either** the graphical method or the command-line method below. The command line is
faster and less error-prone.

### Method A — Command line (recommended)

**Windows (PowerShell).** Open PowerShell, then:

```powershell
cd "$HOME\Documents\Seneca\PRG455.263"

$dirs = "lab1","lab2","lab3","lab4","lab5","lab6","lab7","lab8",
        "labTest1","labTest2","project1","project2"

foreach ($d in $dirs) {
    New-Item -ItemType Directory -Force -Path $d | Out-Null
    Set-Content -Path "$d\README.md" -Value "# $d`n`nPRG455.263`n"
}

Get-ChildItem
```

**macOS or Linux (Terminal).**

```bash
cd ~/Documents/Seneca/PRG455.263

mkdir -p lab1 lab2 lab3 lab4 lab5 lab6 lab7 lab8 labTest1 labTest2 project1 project2

for d in lab1 lab2 lab3 lab4 lab5 lab6 lab7 lab8 labTest1 labTest2 project1 project2; do
    printf '# %s\n\nPRG455.263\n' "$d" > "$d/README.md"
done

ls -1
```

Adjust the `cd` path if you put the repository somewhere else. If the `cd` command reports that
the path does not exist, you have the wrong path — find the folder in Explorer or Finder first
and check.

### Method B — Graphical

1. Open the `PRG455.263` folder in File Explorer or Finder.
2. Create each of the twelve folders by hand: `lab1`, `lab2`, `lab3`, `lab4`, `lab5`,
   `lab6`, `lab7`, `lab8`, `labTest1`, `labTest2`, `project1`, `project2`.
3. Open each folder and create a file called `README.md` inside it containing the folder name.
   The simplest way is to open the folder in VS Code and use **File → New File**.

> **Windows warning:** if you create the file in Notepad, Windows may silently save it as
> `README.md.txt`. In Explorer, turn on **View → Show → File name extensions** so you can see

## Part 6 — Commit and push (10 min)

"Committing" saves a snapshot locally. "Pushing" uploads it to GitHub. Both are needed.

### Step 6.1 — Look at what changed

Switch to GitHub Desktop. The **Changes** tab on the left now lists every new file — twelve or
so, including all the `README.md` files you just created.

**Spend thirty seconds looking at this list.** Click one of the files. The right-hand panel
shows the contents in green, meaning added. Reading the changes before committing is a habit
worth building now; in Week 3 that panel is how you will see exactly what Claude modified in
your code.

### Step 6.2 — Commit

At the bottom left:

1. **Summary:** `setup: create course directory structure`
2. **Description:** leave blank.
3. Click **Commit to main**.

### Step 6.3 — Push

Click **Push origin** at the top of the window. Nothing exists on GitHub until you do this.

### Verification 5

Reload `github.com/<yourusername>/PRG455.263` in your browser. You should see all twelve
folders. Click into `lab1` — you should see its `README.md`.

**If the folders are not there in the browser, they are not submitted.** Check that you pushed.

## Part 7 — The workflow you will use every week

Once your repository exists, the weekly cycle is short:

1. **Open GitHub Desktop before you start working.** Click **Fetch origin** at the top. This
   matters once you start working on more than one machine.
2. **Work in the correct folder.** Lab 3 work goes in `lab3/`. Nowhere else.
3. **Commit often** — after each meaningful step, not once at the end. A repository with a
   single commit reading "done" scores zero on process evidence in this course, regardless of
   whether the code works.
4. **Push before you leave the lab.** Every time.

### Commit message conventions for this course

Use these prefixes so your history is readable at a glance and your instructor can find the
generated-versus-modified diff quickly:

| Prefix | Use it when | Example |
|---|---|---|
| `claude:` | Committing generated output **before** you change it | `claude: generated serial reader from spec` |
| `manual:` | You wrote or changed the code yourself | `manual: fix status label not clearing` |
| `fix:` | Repairing a defect you found | `fix: handle empty entry field` |
| `docs:` | README, PROMPTS.md, notes | `docs: add prompt log entries for lab 3` |
| `setup:` | Structure, configuration, housekeeping | `setup: create course directory structure` |

**The `claude:` commit is not optional.** Commit the generated code exactly as produced, then
commit your corrections separately. That diff is a graded artifact.

### What not to commit

Your `.gitignore` (set to Python when you created the repository) already excludes most of it.
Beyond that:

- No virtual environment folders (`venv/`, `.venv/`)
- No `__pycache__/` folders
- No large binaries, videos, or firmware images unless a lab explicitly asks for them
- **No passwords, API keys, or Wi-Fi credentials.** In Week 10 you will connect the ESP32 to a
  network. Credentials go in a separate file that `.gitignore` excludes. Your repository being
  private does not make this safe: visibility can be changed with two clicks, collaborators can
  read everything, and Git history keeps a copy of a secret forever even after you delete the
  line. Treat anything you commit as permanently readable.

## Troubleshooting

**GitHub Desktop shows "no local changes" after I created folders.**
The folders are empty. Git does not track empty folders. Put a `README.md` in each — see
Part 5.

**I cannot find my repository folder on disk.**
In GitHub Desktop: **Repository → Show in Explorer** (Windows) or **Show in Finder** (macOS).

**"Authentication failed" when pushing.**
Sign out and back in: **Settings → Accounts → Sign out**, then sign in again. Your 2FA code
will be requested.

**My instructor says they cannot see my repository.**
Check three things in order: (1) `github.com/<you>/PRG455.263` → **Settings → Collaborators** —
is `danny-arroway` listed? (2) Has the invitation expired? Invitations lapse after seven days;
remove and re-add if so. (3) Did you push? A commit that exists only on your laptop is invisible
to everyone, private repository or not.

**I registered GitHub with the wrong email address.**
You do not need a new account. On github.com: **Settings → Emails → Add email address**, enter
your Gmail address, verify it from the message GitHub sends, then set it as **Primary**. You may
then remove the old address.

**I set my repository to public by mistake.**
github.com → repository → **Settings** → **Danger Zone** → **Change repository visibility** →
**Make private**. If it was public and contained work from a lab test, tell your instructor —
say so early, because it looks very different explained late.

**I created the repository in the wrong folder.**
Delete the local folder, delete the repository on github.com (**Settings → General → Danger
Zone → Delete this repository**), and start Part 4 again. Do this now, in Week 1, while it
costs you five minutes.

**I named it `PRG455-263` or `prg455.263` by mistake.**
On github.com: **Settings → General → Repository name**, rename it, then in GitHub Desktop
remove and re-clone the repository so the local copy matches.

**My repository is inside OneDrive and Git is behaving strangely.**
Move it out of the synced folder and re-clone from GitHub. This does not resolve itself.

**I lost my phone and cannot get a 2FA code.**
Use one of the recovery codes you saved in Step 1.3. If you did not save them, contact GitHub
Support immediately — recovery is slow and may not succeed.
