# PRG455 — Event Driven Programming
## Lecture 10: Major Project — Design, Architecture, and AI-Assisted Planning

Weeks 3 through 9 each handed you a spec: one hardware capability, one
widget, a clear acceptance test, a lab handout that told you what
"done" looked like before you wrote a line of code. The Major Project
does not do that. **You** decide what it does, which of the seven
hardware/widget pairings from this term it combines, and what "done"
means for your specific idea. That shift — from *implementing a given
spec* to *producing your own* — is this lecture's actual subject. The
code you'll write in Week 11 is the easy part. Deciding what to build,
and building it in a shape that survives contact with real hardware,
is not.

### Learning Objectives

By the end of this lecture, you will be able to:

1. Scope a Major Project idea against a fixed, non-negotiable
   floor — at least **three** distinct hardware capabilities from
   Weeks 3–9, combined on a single, coherent screen or set of
   screens — without over- or under-scoping for a two-week build.
2. Decompose a project idea into a **state model** (what data exists,
   who owns it, what can change it) before deciding on file structure
   or writing any widget code.
3. Produce a written project proposal that identifies every widget,
   every poll-driven vs. event-driven decision, and every point where
   two hardware subsystems interact — the same decomposition skill
   Lecture 6 taught for a single spec, now applied to a spec you wrote
   yourself.
4. Use Claude — both conversationally and agentically via Claude
   Code — appropriately at the *planning* stage, distinguishing what
   AI is good at scoping out from what only you can decide.
5. Identify integration risk before it becomes integration failure:
   which of your chosen subsystems are likely to conflict for screen
   space, `loop()` time, or `M5.update()` ordering, based on confirmed
   findings from Weeks 4–9.
6. Leave this week's lab with a proposal specific enough that Week
   11's implementation is mostly execution, not further design.

### 1. What the Major Project Actually Requires

Before any design conversation is useful, the floor has to be
concrete. The Major Project must combine:

- **At least three** of the seven hardware/widget pairings from
  Weeks 3–9 (touch/Label-Button-Slider, IMU/Bar-Switch, camera/Image,
  microphone/LED, speaker/Spinbox, Wi-Fi/Dropdown) — you are not
  required to use all seven, and attempting all seven in two weeks is
  a scoping mistake, not a display of ambition.
- **A single coherent application**, not three unrelated demos glued
  onto one screen. "Coherent" means: a user looking at your app for
  the first time can tell what it's *for* — a purpose the three (or
  more) subsystems all serve, not three leftover lab exercises that
  happen to share a `setup()` function.
- **The same standards every lab this term has required**: `setup()`/
  `loop()` structure, `Run Once` only, the 10-field header block, a
  `PROMPTS.md` documenting your AI-assisted workflow, and code that
  has actually run on your physical CoreS3 — not code that looks
  correct in the editor.

What it does **not** require: new hardware capabilities beyond what's
been taught, a novel widget outside the course's palette, or a
"real-world" use case graded on ambition. A well-integrated three-
subsystem project, cleanly designed and thoroughly tested, is a
stronger submission than a five-subsystem project where two pieces
don't actually work together.

### 2. Design Before Code — Why This Week Has No New Code

Every prior lecture ended with a worked example you could type in and
run. This one doesn't, on purpose. The single most common failure
mode in a project like this isn't a syntax error or a missed API
detail — it's **starting to write widget code before deciding what
the program's state actually is.** A label placed at a coordinate that
made sense for Lab 3 and a bar placed at a coordinate that made sense
for Lab 4 will not automatically make sense on the same screen, and
"I'll just start building and figure out the layout as I go" is how a
two-week project becomes a one-week scramble in Week 11.

The order that actually works, in this course and in professional
practice, is:

1. **Decide the state** — what data exists in your program, at any
   given moment, regardless of how it's displayed. (§3)
2. **Decide ownership** — for each piece of state, what sets it (a
   sensor read, a widget event, a calculation) and what reads it (a
   display update, a decision, another subsystem).
3. **Decide the widgets** — only now do you pick which of the nine
   widgets displays or collects each piece of state, and where.
4. **Decide the file structure** — one file or several, and if
   several, how they share state.
5. **Write the proposal** — the artifact due this week, described in
   §6.

Code comes in Week 11, after all five of these are settled. This
mirrors exactly what Lecture 6 asked you to do under time pressure for
a single, given spec — this week asks for the same decomposition, but
for a spec you're writing yourself, with more room to think.

### 3. State First: What Data Does Your Program Actually Hold?

"State" means every piece of information your program needs to
remember between one pass through `loop()` and the next. This is not
a new concept — every lab this term has had state, you just haven't
had to name it explicitly, because each lab only had one or two things
worth tracking. A combined project usually has five to ten, and if you
don't write them down, you will lose track of one and it will surface
as a bug that looks like a hardware problem but isn't.

A concrete way to find your project's state: for each hardware
capability you plan to include, ask **"what does this subsystem
produce that something else needs to know about?"**

| Subsystem | Produces (example state) |
|---|---|
| IMU | current tilt angle, a `calibrated` boolean |
| Microphone | current peak amplitude, a running word/sound count |
| Speaker | a `currently_playing` boolean |
| Wi-Fi | `isconnected()`, selected network profile |
| Camera | path to the most recently captured image |
| Touch (button/slider/switch) | whatever mode or parameter it sets |

Once you have this list, the interesting design questions appear on
their own: **Does the microphone's amplitude reading need to affect
what the speaker plays? Does a Wi-Fi disconnect need to change what's
shown on a screen that's otherwise about the camera?** Projects that
feel "integrated" rather than "three demos taped together" are exactly
the ones where state from one subsystem visibly affects another,
somewhere in the design — that's a design choice to make deliberately
now, not something to hope emerges while coding in Week 11.

> **This is also where over-scoping gets caught early.** If your list
> of state has twelve entries and you can't yet say which of them
> interact, that's a signal to cut scope now, in writing, rather than
> discover it's too much three days before the deadline.

### 4. Ownership and the Poll-vs-Event Question, Applied to a Whole Program

Lecture 6 established that every widget update in this course is
either poll-driven (checked fresh every `loop()` pass) or event-driven
(runs once, in response to a specific action). That question doesn't
go away when subsystems combine — it gets asked **once per piece of
state**, and the answers don't have to match across subsystems just
because they're running in the same program.

A realistic three-subsystem project mixes both, in the same `loop()`,
exactly as Lab 4 first showed with its bar-and-switch pairing:

```python
def loop():
    M5.update()

    # Poll-driven: IMU tilt, checked every pass, regardless of touch
    ax, ay, az = M5.Imu.getAccel()
    tilt_bar.set_value(scale(ax), ANIM_OFF)

    # Poll-driven: Wi-Fi status, can change on its own at any time
    if wlan.isconnected():
        wifi_label.set_text("Wi-Fi: Connected")
    else:
        wifi_label.set_text("Wi-Fi: Not Connected")

    M5.update()

# Event-driven: only runs when the button is actually pressed
def capture_button_clicked(event_struct):
    path = "/flash/img/capture.jpg"
    CoreS3.Camera.capture(path)
    preview_image.set_image(path)
```

Nothing here is a new pattern. What's new is **deciding, for your
specific project, which of your five-to-ten state entries belongs on
which side of that line, before you write the file** — the same
decision Lecture 6 asked you to make quickly under test pressure, now
made carefully, in advance, for a program you designed.

### 5. Integration Risk: Where Two Subsystems Actually Conflict

Combining subsystems introduces failure modes that don't exist when
each one runs alone in its own lab file. Three specific risks, each
grounded in a confirmed finding from earlier this term, are worth
checking against your own design **before** Week 11:

**Screen space.** Every widget in every lab so far has had the whole
screen to itself or shared it with one or two others. A three-or-more
subsystem project puts everything on one 320×240 display at once.
Sketch rough coordinates for every widget now, the same habit Lecture
6 asked for spec-reading — a label with no fixed box (Week 3's
`M5Label` gotcha) that grows into space you'd planned for something
else is a layout bug you can catch on paper, before it's a layout bug
on a physical screen.

**`loop()` timing.** Every poll-driven read you add executes on every
single pass through `loop()`, every time, regardless of what else is
happening. A `loop()` that reads the IMU, checks Wi-Fi status, and
polls a microphone buffer all every pass is doing meaningfully more
work per pass than any single lab did alone. This rarely breaks a
project outright, but it's worth being deliberate about which reads
genuinely need to happen every pass versus which could be
event-triggered instead — a design decision, not a performance
optimization to defer.

**Non-blocking operations that don't know about each other.** Weeks
7–9 each introduced a hardware call that starts something in the
background rather than blocking until it finishes:
`Mic.record()`, `Speaker.tone()`, `wlan.connect()`. Each week's
material showed you how to guard *that one call* against being
invoked again before it settles. **A combined project raises a new
question those single-subsystem labs didn't have to answer: can two
different background operations from two different subsystems be
in flight at the same time, and if so, does your design care?** If
your project plays a tone *and* attempts a Wi-Fi reconnect from the
same button press, that's worth thinking through now, not discovering
as an intermittent bug in Week 11.

None of these three risks require new code this week. They require
you to look at your own state list from §3 and your own widget layout
from §4, and ask "where do these collide" — the same close reading
Lecture 6 asked you to apply to an unfamiliar spec, now applied to a
spec of your own making.

### 6. Using Claude at the Planning Stage — What It's Good For Here

Every reading this term has used Claude for something narrower than
"write my project": generating a function, diagnosing a confirmed
error, refactoring a file. Planning is a genuinely different use, and
it's worth being explicit about what AI is and isn't well-suited to
at this stage.

**Good uses of Claude while planning:**

- **Sanity-checking scope.** Describe your three-or-more-subsystem
  idea in a sentence or two and ask whether it's a reasonable
  two-week build given everything covered this term — not "build
  this for me," but "is this the right size."
- **Surfacing integration questions you haven't thought of.** Once
  you've listed your state (§3), ask Claude to list every place two
  of your subsystems might interact — screen space, `loop()` load, or
  a background operation overlap like §5 describes — and treat the
  answer as a checklist to verify against your own design, not as a
  design decision made for you.
- **Drafting the proposal document itself.** Once you know your state
  list, your widget choices, and your layout, asking Claude to help
  structure that into a clear written proposal (§7) is exactly the
  same kind of writing-assistance use this course has encouraged with
  READMEs and comments all term.
- **Using Claude Code in Plan Mode** (introduced in
  `9.2_agentic_AI_and_Claude_Code.md`) to explore your *existing*
  lab repositories — "what would need to change to combine lab6/ and
  lab8/ into one page" — without letting it write anything yet. Plan
  Mode's read-only exploration is exactly suited to this week's task:
  understanding the shape of a change before committing to it.

**What Claude cannot do for you at this stage:** decide what your
project is *for*, decide which three subsystems best serve that
purpose, or decide the trade-off between scope and reliability that
only you can make given your own time and confidence with the
material. An AI-generated project idea you don't have a clear reason
for choosing is a weaker proposal than a simpler idea you can explain
and defend — the same academic-integrity expectation this course has
held since Week 1 applies to planning as much as it does to code:
**you are responsible for the decisions, even when AI helped you think
them through.**

> **`PROMPTS.md` starts this week, not in Week 11.** If you use
> Claude to sanity-check scope, surface integration risks, or draft
> your proposal, that's AI assistance on a graded deliverable and
> belongs in the log exactly as much as AI-generated code does.

### 7. The Proposal — This Week's Deliverable

Monday's lab session is project work time built around producing a
short written proposal, reviewed with your instructor before Week 11
implementation begins. A proposal that lets Week 11 be mostly
execution rather than further design should include:

1. **One-paragraph purpose statement.** What is this application for?
   A user unfamiliar with the course should be able to read this and
   understand the point, not just the mechanism.
2. **Subsystem list.** Which three-or-more hardware/widget pairings
   from Weeks 3–9 are included, and one sentence on what each
   contributes to the stated purpose.
3. **State table.** The list from §3 — what data exists, produced by
   which subsystem, needed by what else.
4. **Poll vs. event decision, per state entry.** The table from §4,
   filled in for your specific design.
5. **Rough layout sketch.** Approximate widget positions on the
   320×240 screen — hand-drawn, described in coordinates, or built as
   a quick mockup; the level of detail from Lecture 6 §4's step 4
   applies here.
6. **Integration risk check.** For each of the three risks in §5,
   one sentence on whether it applies to your design and, if so, how
   you plan to handle it.
7. **File structure.** One file or several; if several, how state is
   shared between them (module-level variables, a shared constants
   file, or another pattern — whatever you choose, name it).

This document does not need to be long. It needs to be **specific
enough that someone else reading it could start implementing your
design without having to ask you what you meant** — the same bar this
course has held prior lab specs to, now applied to a spec you wrote.

### 8. Key Takeaways

- The Major Project's floor is fixed and known: **at least three**
  Weeks 3–9 hardware/widget pairings, combined into one coherent
  application, built to the same standards every lab this term has
  required.
- **Design comes before code.** State first (§3), then ownership and
  poll-vs-event per state entry (§4), then widget choice and layout,
  then file structure — in that order, not worked out while typing.
- Combining subsystems introduces integration risks that don't exist
  in any single lab: screen space, `loop()` load, and background
  operations from different subsystems potentially overlapping. All
  three are checkable on paper, this week, against your own design.
- Claude is genuinely useful at the planning stage — for scope
  sanity-checks, surfacing integration questions, drafting the
  proposal, and Plan Mode exploration of existing repos — but the
  purpose, the subsystem choice, and the scope/reliability trade-off
  are decisions only you can make and are expected to be able to
  explain.
- `PROMPTS.md` logging starts with this week's planning work, not
  with Week 11's code.
- This week's lab deliverable is a written proposal (§7), specific
  enough that Week 11 is mostly implementation rather than further
  design.
