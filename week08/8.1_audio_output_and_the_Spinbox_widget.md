### 1. The Speaker: CoreS3's Audio Output

Every hardware capability this course has covered so far has been an
**input** — touch, tilt, a camera frame, a microphone buffer. The
speaker is this course's first **output**: instead of reading
something from the world, your program produces a sound the world can
hear. The core API is small and direct:

```python
Speaker.begin()
Speaker.tone(880, 300)   # play 880 Hz for 300 milliseconds
```

- **`Speaker.begin()`** starts the speaker hardware. Call it once in
  `setup()`, the same way `Mic.begin()` was called once in Lecture 7.
- **`Speaker.tone(frequency, duration)`** plays a single tone.
  `frequency` is in Hz (a rough audible range for this hardware is
  roughly 100–5000 Hz — very low or very high values may sound faint
  or not play cleanly); `duration` is in milliseconds.

Two more methods matter for anything beyond a single beep:

```python
Speaker.setVolumePercentage(60)   # 0-100
playing = Speaker.isPlaying()      # True while a sound is still going
```

`Speaker.tone()` does **not** block your program while the tone
plays — control returns to your code immediately, and the sound plays
in the background. `Speaker.isPlaying()` is how you check whether a
previously triggered tone has finished, the same role
`Mic.isRecording()` played for checking whether a microphone buffer
was ready.

> **Gotcha — the mic and speaker share the same I2S hardware and
> cannot run at the same time.** This was flagged from the
> microphone's side in Lecture 7; it applies equally here. If a
> program in this course ever needs both — for example, a future
> project that records and plays back audio — call `Mic.end()` before
> `Speaker.begin()`, and `Speaker.end()`/`Speaker.stop()` before
> `Mic.begin()`, rather than assuming both can be initialized at once.

> **Confirm exact method names and behavior against the widget in
> UIFlow2 before relying on them.** As with every new widget in this
> course, the API shown here reflects the documented UIFlow2
> MicroPython interface, but this lecture has not yet been run
> against a physical CoreS3. Treat any surprising behavior (a
> parameter order that doesn't match, a call that raises an
> unexpected error) the way every prior lecture's confirmed-findings
> table was built: test on real hardware, note what actually happens,
> and adjust.

### 2. `M5Spinbox` — a Numeric Input with Built-In Limits

Every widget so far that produces a number — `M5Slider`, `M5Bar` —
required *you* to clamp-and-scale a raw value into a sensible range.
`M5Spinbox` is different: it's a numeric input where the **range is
enforced by the widget itself**, and the widget refuses to go outside
it.

```python
spinbox0 = m5ui.M5Spinbox(
    x=40, y=80, w=160, h=50,
    value=440, min_value=100, max_value=5000,
    digit_count=4, prec=0,
    font=lv.font_montserrat_14,
    parent=page0,
)
```

| Constructor argument | Meaning |
|---|---|
| `x`, `y`, `w`, `h` | Position and size, same as every other widget |
| `value` | The spinbox's starting value |
| `min_value`, `max_value` | The inclusive range the spinbox is allowed to hold |
| `digit_count` | How many digits the spinbox displays — big enough to show `max_value` in full |
| `prec` | Decimal places shown; `0` for whole numbers like a frequency in Hz |
| `font` | Same LVGL font object every other M5UI text widget uses |
| `parent` | The page it belongs to, same as always |

> **`step` is not a constructor argument, and it doesn't mean what it
> sounds like it means.** The step size is set *after* construction
> with `spinbox0.set_step(step)` — passing `step=` into
> `M5Spinbox(...)` raises a `TypeError`. More importantly: under the
> hood, a spinbox's step is not "how much the value changes per
> press" in the way a slider's step is. It's **which decimal digit
> position** increment/decrement operates on, and it must be a power
> of ten — `1`, `10`, `100`, `1000`, and so on. Calling
> `spinbox0.set_step(50)` doesn't raise an error; it silently rounds
> up to the nearest valid digit step (`500`, since `50` isn't a valid
> digit position) and logs a warning like `No decimal places, step 50
> converted to 500.` If you actually need increments of `50`, `set_step()`
> alone cannot give you that — see the workaround below.

> **A related, sharper-edged gotcha: `get_value()` can return a
> `float`, not an `int`.** The documented return type is `float |
> int`. Passing that value straight into a function that requires an
> integer — `Speaker.tone(frequency, duration)` is exactly this case —
> can raise `TypeError: can't convert float to int` even though the
> value looks like a whole number on screen. **Always wrap a
> spinbox's value in `int()` before handing it to something that
> requires an integer:** `Speaker.tone(int(spinbox0.get_value()),
> duration)`. This costs nothing when the value already is a whole
> number, and it removes an entire category of hard-to-predict
> failures.

**A tempting but broken fix, and why it breaks.** A natural first
instinct is to keep `min_value=100`/`max_value=5000` from a power-of-
ten step and separately *snap* the value to the nearest multiple of
`50` inside the `VALUE_CHANGED` handler, writing the corrected number
back with `spinbox0.set_value()`. Tried in isolation against a single
external write, this looks safe. It is **not** safe against the
widget's own increment/decrement buttons, and produces a very specific
symptom: the spinbox appears to work until the value lands on a real
multiple of `50` — say `450` — and then **freezes**, refusing to move
any further in either direction, with no error and no feedback.

Here's why: once the spinbox sits at `450`, the *next* physical press
still moves the widget by its own internal step (e.g. `+1`, landing on
`451`) and fires `VALUE_CHANGED`. The handler sees `451`, rounds it
back down to `450`, and calls `set_value(450)` — which is a *different*
value from `451`, so it re-fires `VALUE_CHANGED` again. That next call
sees `450` (already a multiple of `50`), does nothing further, and
returns — but the very next physical press repeats the exact same
cycle: `450 → (press) → 451 → snap → 450`. The number on screen never
changes again, no matter how many times the button is pressed. The
earlier reasoning that this approach was "safe because the rounding
function is idempotent" was true for a *single* external write — it
does not hold once the widget's own controls keep nudging the value
by their own step on every subsequent press, which is exactly what
increment/decrement buttons do.

**The correct fix: don't fight the widget's own step.** Rather than
trying to force a non-power-of-ten increment by rewriting the
spinbox's value after the fact, set a valid power-of-ten step that's
close to what you actually want, and let the widget move freely with
no write-back at all:

```python
spinbox0.set_step(10)
```

`10` is the largest valid power-of-ten step at or below `50`. This
gives up exact 50-unit increments in exchange for a spinbox that never
fights its own controls — a good trade, since a frozen input is worse
than a slightly finer-grained one. If a project genuinely needs an
increment that isn't a power of ten, the safe way to get it is a
**separate button pair you build yourself** (e.g. `+50`/`-50` buttons
that call `spinbox0.set_value(spinbox0.get_value() + 50)` directly,
never reacting to the spinbox's own `VALUE_CHANGED` event to correct
it) — not a correction layered on top of the spinbox's native
controls.

Once built, a spinbox is adjusted with its own increment/decrement
controls (typically small `+`/`-` buttons rendered as part of the
widget) rather than free typing — matching this course's rule that
free-text entry via the on-screen keyboard is off-limits for graded
work. Reading and setting its value programmatically:

```python
current = int(spinbox0.get_value())
spinbox0.set_value(880)
spinbox0.set_range(100, 5000)   # can also be changed after construction
```

> **Why the range half of this is still a genuinely different shape
> from every prior numeric widget.** `M5Slider` and `M5Bar` will
> happily accept any value your code hands them — clamping was *your*
> job, and forgetting it meant a percentage over 100 or a bar past its
> max. A spinbox enforces `min_value`/`max_value` itself: calling
> `set_value()` with something outside the range simply doesn't move
> the value past the limit. This doesn't
> eliminate clamp-and-scale as a concept — you'll still need it the
> moment a spinbox's integer value has to drive something with a
> *different* range, like a frequency in Hz feeding a percentage-based
> volume — but it does mean the spinbox's own value can never itself
> be invalid.

### 3. Responding to Spinbox Changes

A spinbox raises the same kind of `VALUE_CHANGED` event every other
interactive widget in this course does, following the identical
pattern established for `M5Switch` in Lecture 4:

```python
def spinbox0_changed(event_struct):
    freq_label.set_text("Frequency: %d Hz" % int(spinbox0.get_value()))


def spinbox0_handler(event_struct):
    if event_struct.code == lv.EVENT.VALUE_CHANGED:
        spinbox0_changed(event_struct)
    return
```

```python
spinbox0.add_event_cb(spinbox0_handler, lv.EVENT.ALL, None)
```

Nothing new about the *shape* of this — same `add_event_cb`, same
`lv.EVENT.VALUE_CHANGED` check, same separation between the raw
handler and a named function describing what actually happened. What's
new is what triggers it: an increment/decrement press on the spinbox,
rather than a slider drag or a switch flip.

### 4. Event-Driven Control, Event-Driven Action

Every worked example since Lecture 4 has paired one **poll-driven**
sensor reading (updated every `loop()` pass) with one **event-driven**
control (updated only on touch). This lecture's worked example is
different: **both halves are event-driven.** There's no sensor to poll
— the spinbox holds whatever value the user last set, and a button
press triggers the speaker using that value at the moment of the
press.

```python
def play_button_pressed(event_struct):
    freq = int(spinbox0.get_value())
    Speaker.tone(freq, 300)


def play_button_handler(event_struct):
    if event_struct.code == lv.EVENT.CLICKED:
        play_button_pressed(event_struct)
    return
```

`loop()` in a program shaped like this can be almost empty — just
`M5.update()` — because nothing needs to be continuously recalculated.
This is worth noticing explicitly: not every program in this course
needs meaningful work happening every pass through `loop()`. A
sensor-driven meter does; a purely on-demand tool like a tone
generator doesn't. Recognizing which shape a given program calls for
is itself part of the design skill this course has been building.

### 5. Worked Example — Spinbox Tone Generator

A single-screen app: a spinbox sets a frequency, a label shows the
current setting, and a button plays that frequency as a tone through
the speaker.

```python
# SPDX-License-Identifier: MIT
#
# PRG455 Lecture 8 -- Spinbox Tone Generator
# Demonstrates the speaker (Speaker.begin()/tone()), M5Spinbox (a
# numeric input with a built-in, self-enforcing range, unlike
# M5Slider/M5Bar which required manual clamp-and-scale), the int()
# cast needed before handing a spinbox value to Speaker.tone(), and
# an event-driven-only program shape: no polling in loop(), since
# nothing needs continuous recalculation.
#
# NOTE on step size: set_step() only accepts powers of ten
# (1/10/100/1000...), so this example uses a step of 10 rather than a
# non-power-of-ten value like 50. An earlier version of this example
# tried to fake a 50-unit step by snapping the value back with
# set_value() inside the VALUE_CHANGED handler -- that approach
# freezes the spinbox the moment its value lands on an exact multiple
# of 50, because the widget's own increment/decrement buttons keep
# nudging the value by their own step on every press, fighting the
# snap-back forever. Using a valid native step avoids this entirely.

import os, sys, io
import M5
from M5 import *
import m5ui
import lvgl as lv

ANIM_OFF = getattr(lv, "ANIM_OFF", 0)

page0 = None
title_label = None
spinbox0 = None
freq_label = None
play_button = None

TONE_DURATION_MS = 300
MIN_FREQ = 100
MAX_FREQ = 5000
FREQ_STEP = 10   # must be a power of ten -- see the NOTE above
DEFAULT_FREQ = 440


def spinbox0_changed(event_struct):
    # int() is required: get_value() is documented to return
    # float | int, and this label formats it as a whole-number Hz
    # value.
    freq_label.set_text("Frequency: %d Hz" % int(spinbox0.get_value()))


def spinbox0_handler(event_struct):
    if event_struct.code == lv.EVENT.VALUE_CHANGED:
        spinbox0_changed(event_struct)
    return


def play_button_pressed(event_struct):
    # int() is required here: M5Spinbox.get_value() is documented to
    # return float | int, and Speaker.tone() requires an integer
    # frequency -- skipping this cast can raise
    # "TypeError: can't convert float to int" even when the spinbox
    # is showing what looks like a whole number.
    freq = int(spinbox0.get_value())
    Speaker.tone(freq, TONE_DURATION_MS)


def play_button_handler(event_struct):
    if event_struct.code == lv.EVENT.CLICKED:
        play_button_pressed(event_struct)
    return


def setup():
    global page0, title_label, spinbox0, freq_label, play_button

    M5.begin()
    Widgets.setRotation(1)
    m5ui.init()
    page0 = m5ui.M5Page(bg_c=0xFFFFFF)

    title_font = getattr(lv, "font_montserrat_20", lv.font_montserrat_14)
    title_label = m5ui.M5Label(
        "Tone Generator", x=10, y=4,
        text_c=0x000000, bg_c=0xFFFFFF, bg_opa=0,
        font=title_font, parent=page0,
    )

    spinbox0 = m5ui.M5Spinbox(
        x=40, y=60, w=160, h=50,
        value=DEFAULT_FREQ, min_value=MIN_FREQ, max_value=MAX_FREQ,
        digit_count=4, prec=0,
        font=lv.font_montserrat_14,
        parent=page0,
    )
    spinbox0.set_step(FREQ_STEP)   # 10 is a valid power-of-ten step
    spinbox0.add_event_cb(spinbox0_handler, lv.EVENT.ALL, None)

    freq_label = m5ui.M5Label(
        "Frequency: %d Hz" % DEFAULT_FREQ, x=10, y=124,
        text_c=0x000000, bg_c=0xFFFFFF, bg_opa=0,
        font=lv.font_montserrat_14, parent=page0,
    )

    play_button = m5ui.M5Button(
        text="Play Tone", x=90, y=160, w=140, h=50,
        bg_c=0x2196F3, text_c=0xFFFFFF,
        parent=page0,
    )
    play_button.add_event_cb(play_button_handler, lv.EVENT.ALL, None)

    Speaker.begin()

    page0.screen_load()


def loop():
    # Nothing to poll -- the spinbox holds its own value until
    # changed, and the speaker is only ever triggered by a button
    # press. M5.update() is still required every pass so the UI and
    # touch input keep working.
    M5.update()


if __name__ == '__main__':
    try:
        setup()
        while True:
            loop()
    except (Exception, KeyboardInterrupt) as e:
        try:
            m5ui.deinit()
            from utility import print_error_msg
            print_error_msg(e)
        except ImportError:
            print("please update to latest firmware")
```

### 6. Key Takeaways

- The speaker is this course's first **output** device: your program
  produces sound rather than reading a sensor. `Speaker.begin()` once
  in `setup()`, then `Speaker.tone(frequency, duration)` whenever a
  sound is needed.
- `Speaker.tone()` is **non-blocking** — it returns immediately while
  the tone plays in the background. `Speaker.isPlaying()` checks
  whether a previously triggered sound is still going, the same role
  `Mic.isRecording()` played for the microphone.
- **The mic and speaker share the same I2S hardware and cannot run at
  the same time** — the same gotcha from Lecture 7, relevant now that
  a program could plausibly need both.
- `M5Spinbox` is the first numeric widget in this course with a
  **built-in, self-enforcing range** — `min_value`/`max_value` are
  enforced by the widget itself, unlike `M5Slider`/`M5Bar`, which
  required you to clamp-and-scale by hand. This doesn't retire
  clamp-and-scale as a technique — it's still needed the moment a
  spinbox's value has to drive something with a different range — but
  it does mean the spinbox's own value is always within range by
  construction.
- **`step` is not a constructor argument, and it isn't an arbitrary
  increment.** `spinbox0.set_step(step)` only accepts powers of ten
  (`1`, `10`, `100`, `1000`...) — it selects which digit position
  increment/decrement operates on. Passing a value like `50` doesn't
  raise an error; it silently rounds up to the nearest valid digit
  step and logs a warning.
- **Do not try to fake a non-power-of-ten step by snapping the value
  back with `set_value()` inside `VALUE_CHANGED`.** This looks safe
  against a single external write, but freezes the spinbox the
  instant its value lands on an exact multiple of your target step —
  the widget's own increment/decrement controls keep nudging the
  value by their own native step on every subsequent press, and the
  snap-back fights that forever. Use the nearest valid power-of-ten
  step instead, or build separate custom increment buttons that never
  react to the spinbox's own `VALUE_CHANGED` event.
- **`get_value()` can return a `float`.** Always wrap it in `int()`
  before passing it to something that requires an integer, such as
  `Speaker.tone()` — skipping this can raise `TypeError: can't
  convert float to int` even when the displayed value looks like a
  whole number.
- A spinbox raises the same `VALUE_CHANGED` event every interactive
  widget in this course has used since Lecture 4 — `add_event_cb`,
  `lv.EVENT.VALUE_CHANGED`, a named handler function. Nothing new
  about the event-handling shape, only about what's being adjusted.
- Not every program needs meaningful work in `loop()`. This lecture's
  worked example is **entirely event-driven** — a spinbox holds its
  value until changed, a button triggers the speaker at the moment of
  the press — and `loop()` only needs `M5.update()`. Recognizing when
  a program doesn't need a poll-driven half is as important as
  building the poll-driven programs from Lectures 4–7.
