# PRG455 — Event Driven Programming
## Lecture 9: Wireless Connectivity — the Dropdown Widget

Weeks 3 through 8 each paired one Core S3 hardware capability with one
M5UI widget. This week closes out that pattern with the last new
widget this course introduces before project work begins:
**Wi-Fi connectivity**, paired with **`M5Dropdown`**.

Unlike touch, motion, camera, microphone, and speaker, Wi-Fi is not a
sensor or actuator built into a single chip you poll or drive — it's
a **network interface** with its own connection lifecycle: off, on
but not connected, connecting, connected, or disconnected again
without warning. Handling that lifecycle well, rather than assuming
"connected" is a permanent state, is this lecture's real subject.

### Learning Objectives

By the end of this lecture, you will be able to:

1. Create a Wi-Fi station interface with `network.WLAN(network.STA_IF)`,
   activate it with `.active(True)`, and connect with `.connect(ssid,
   password)`.
2. Check connection state with `.isconnected()` and read signal
   strength with `.status('rssi')`.
3. Recognize that a Wi-Fi connection is not a one-time event but a
   **lifecycle** that must be polled, since the device can lose and
   regain a connection at any time without your code doing anything.
4. Create and configure an `M5Dropdown` — a compact widget for
   choosing one option from a list, expanding open on touch and
   collapsing after a selection.
5. Read a dropdown's current selection with `get_selected_str()`/
   `get_selected()`, and respond to a selection from a `VALUE_CHANGED`

6. Combine a poll-driven connection-status display with an
   event-driven dropdown selection, the same two-halves shape used
   for the IMU/switch, microphone/switch, and camera/button pairings
   in prior weeks.

### 1. Wi-Fi Is Not "On or Off" — It's a Lifecycle

Every hardware capability so far in this course has had a simple
availability story: the IMU is always there once `M5.begin()` runs,
the camera works once you call `camera.init()`, the microphone works
once you call `Mic.begin()`. Wi-Fi is different in one important way:
**a Wi-Fi connection can be lost at any moment for reasons entirely
outside your program's control** — the access point goes down, the
device walks out of range, the router reboots. Code that assumes "once
connected, always connected" will work perfectly in a demo and fail
the first time it's used somewhere with real, imperfect Wi-Fi.

The interface itself, confirmed from the official MicroPython network
API on this hardware:

```python
import network

wlan = network.WLAN(network.STA_IF)   # STA = "station", i.e. client mode
wlan.active(True)                      # turn the radio on
wlan.connect("your-ssid", "your-password")
```

- **`network.STA_IF`** puts the CoreS3 in **station mode** — it
  connects *to* an existing Wi-Fi network, the same way a laptop or
  phone does. (The alternative, `network.AP_IF`, makes the CoreS3
  broadcast its *own* network — out of scope for this lecture.)
- **`.active(True)`** must be called before `.connect()` will do
  anything — this mirrors the confirmed finding from earlier in this
  course that `.active(True)` is required before `.config('mac')`
  works, for the same underlying reason: the radio has to be powered
  on before most other calls are meaningful.
- **`.connect(ssid, password)`** starts a connection attempt.
  Critically, **this call does not wait for the connection to
  succeed** — like `Mic.record()` and `Speaker.tone()` before it,
  it kicks off something that happens in the background.

### 2. Checking Connection State — Poll, Don't Assume

Because `.connect()` doesn't block, and because a connection can drop
at any later time, this course's answer is the same one it's used for
every non-blocking operation since Lecture 7: **check, don't assume**.

```python
connected = wlan.isconnected()   # True only once actually connected
rssi = wlan.status('rssi')        # signal strength in dBm, once connected
```

- **`.isconnected()`** is the one fact your program can trust. It
  returns `False` immediately after `.connect()` is called (the
  handshake hasn't finished yet), `True` once the connection succeeds,
  and — this is the part every prior widget in this course hasn't
  needed you to think about — **it can go back to `False` later, on
  its own, with no code of yours causing it.**
- **`.status('rssi')`** reports signal strength once connected, useful
  for a "how good is this connection" display, but only meaningful
  when `.isconnected()` is `True` — calling it while disconnected
  doesn't raise an error, but the number returned isn't a live signal
  reading.

> **This is why Wi-Fi status belongs in `loop()`, not just in
> `setup()`.** Calling `.connect()` once in `setup()` and never
> checking again is the Wi-Fi equivalent of reading the IMU once at
> startup and displaying that number for the rest of the program's
> life — technically code that runs, but not code that reflects
> reality. A connection status label, like the tilt bar in Lecture 4
> or the level meter in Lecture 7, needs to be **re-checked every
> pass through `loop()`** to stay honest.

> **Confirmed on hardware — calling `.connect()` again while a
> previous attempt is still resolving crashes the program.** This is
> the first genuinely dangerous gotcha in this course's Wi-Fi
> material, confirmed by testing this lecture's own worked example: if
> a user selects one dropdown option, then selects a **different**
> option (or even the same one again) before the first `.connect()`
> call has finished resolving — succeeded, failed, or timed out —
> the second `.connect()` call raises `OSError: Wifi Internal State
> Error`. This is a documented, reproducible ESP32 MicroPython
> behavior, not something specific to this course's code — the same
> error appears in MicroPython's own issue tracker under exactly this
> condition. Because the exception happens inside the dropdown's own
> event handler, it isn't silently absorbed the way some MicroPython
> event dispatch failures are — it propagates and **freezes the whole
> app**.
>
> The fix is to never call `.connect()` unconditionally. Disconnect
> first if already connected, and wrap the connect attempt in a
> `try`/`except OSError` so a rejected attempt can never crash the
> program — it simply fails gracefully, and the existing
> `loop()`-driven status check keeps reporting the true connection
> state on the next pass regardless:
>
> ```python
> def safe_connect(ssid, password):
>     try:
>         if wlan.isconnected():
>             wlan.disconnect()
>         wlan.connect(ssid, password)
>         return True
>     except OSError:
>         return False
> ```
>
> This mirrors a principle already established for the microphone and
> speaker in Lectures 7 and 8: a call that "kicks off something in the
> background" needs to be guarded against being invoked again before
> the prior attempt has settled. The worked example in §6 below uses
> this pattern for exactly this reason.

> **Still to confirm on your own hardware: automatic reconnection
> after a dropped connection.** The crash above is now confirmed and
> fixed; a separate, still-open question is what happens when a
> working connection is lost on its own (walking out of range, the
> access point restarting). Some firmware configurations retry
> automatically (`wlan.config(reconnects=N)` controls this on some
> UIFlow2 versions); others require your own code to notice
> `isconnected()` return `False` and call `.connect()` again — now
> safely, via `safe_connect()`. Test what your specific firmware build
> does before assuming either behavior.

### 3. `M5Dropdown` — Choosing One Option From a List

`M5Dropdown` fills a gap the existing widget palette has: a compact
way to choose one option out of several, without the screen space a
row of buttons would need, and without the free-text entry this
course's rules exclude. Confirmed constructor and core methods from
the official M5UI API:

```python
dropdown0 = m5ui.M5Dropdown(
    x=10, y=40, w=200, h=lv.SIZE_CONTENT,
    options=["Home", "Office", "Mobile Hotspot"],
    direction=lv.DIR.BOTTOM,
    show_selected=True,
    font=lv.font_montserrat_14,
    parent=page0,
)
```

| Constructor argument | Meaning |
|---|---|
| `x`, `y`, `w` | Position and width, same as every other widget |
| `h` | Height — `lv.SIZE_CONTENT` lets the widget size itself to fit its text, rather than a fixed pixel value |
| `options` | A Python list of strings — the choices shown when the dropdown is opened |
| `direction` | Which way the option list expands: `lv.DIR.BOTTOM`, `TOP`, `LEFT`, or `RIGHT` — pick whichever won't run off the edge of the screen given the widget's position |
| `show_selected` | Whether the currently selected option is visually highlighted in the open list |
| `font` | Same LVGL font object every other M5UI text widget uses |
| `parent` | The page it belongs to, same as always |

Reading the current selection:

```python
index = dropdown0.get_selected()        # integer index into options
text = dropdown0.get_selected_str()      # the option text itself
```

Both are valid ways to read the same underlying selection — pick
whichever fits the logic you're writing. `get_selected_str()` is
usually more convenient for display; `get_selected()` is more
convenient when the option chosen needs to drive a lookup into some
other list or dictionary keyed by position.

> **Changing the option list after construction.** `set_options(list)`
> replaces the whole list, `add_option(text, pos)` inserts one option
> at a specific position, and `clear_options()` empties it entirely.
> This matters for a dropdown whose choices depend on something
> discovered at runtime — for example, a real network scanner would
> populate a dropdown's options from `wlan.scan()` results rather than
> a fixed list typed into the code, though that's beyond what this
> lecture's worked example needs.

### 4. Responding to a Selection

`M5Dropdown` raises the same `VALUE_CHANGED` event every interactive
widget in this course has used since Lecture 4, confirmed directly
from the official API example:

```python
def dropdown0_changed(event_struct):
    selected = dropdown0.get_selected_str()
    network_label.set_text("Network: %s" % selected)


def dropdown0_handler(event_struct):
    if event_struct.code == lv.EVENT.VALUE_CHANGED:
        dropdown0_changed(event_struct)
    return


dropdown0.add_event_cb(dropdown0_handler, lv.EVENT.ALL, None)
```

Nothing new about this shape — same `add_event_cb`, same
`lv.EVENT.VALUE_CHANGED` check, same separation between the raw
handler and a named function. What's new is only what's being
selected: one string out of a fixed list, rather than a numeric value
or an on/off state.

### 5. Poll-Driven Status, Event-Driven Selection

This lecture's worked example returns to the two-halves shape from
Lectures 4, 6, and 7: one thing updated every `loop()` pass because
its truth can change on its own (the Wi-Fi connection status), and one
thing updated only when touched (the dropdown selection).

```python
def loop():
    M5.update()
    if wlan.isconnected():
        status_label.set_text("Wi-Fi: Connected")
    else:
        status_label.set_text("Wi-Fi: Not Connected")
```

This is the same shape as the tilt bar in Lecture 4 and the sound
level meter in Lecture 7 — a value that can change for reasons outside
any button press, checked fresh on every pass, rather than computed
once and trusted forever.

### 6. Worked Example — Network Selector

A single-screen app: a dropdown lets the user pick which saved network
profile to use, and a status label continuously reflects whether the
CoreS3 is actually connected right now.

```python
# SPDX-License-Identifier: MIT
#
# PRG455 Lecture 9 -- Network Selector
# Demonstrates Wi-Fi station mode (network.WLAN(STA_IF), .active(),
# .connect(), .isconnected()), M5Dropdown (choosing one option from a
# fixed list, the VALUE_CHANGED event pattern used since Lecture 4),
# and the poll-driven status + event-driven selection shape used
# since Lecture 4.
#
# CONFIRMED ON HARDWARE: calling wlan.connect() again while a previous
# attempt is still resolving raises OSError: Wifi Internal State
# Error -- reproducible by selecting a second dropdown option (or
# re-selecting the same one) before the first connection attempt has
# settled. Because this happens inside the dropdown's own event
# handler, the exception is not silently absorbed -- it freezes the
# whole app. safe_connect() below guards against this: it disconnects
# first if already connected, and wraps the connect() attempt in
# try/except OSError so a rejected attempt can never crash the
# program. See section 2 above for the full explanation.
#
# NOTE: the SSID/password pairs below are placeholders. Replace them
# with real network credentials on your own hardware, or this example
# will call .connect() and simply never reach isconnected() == True --
# which is itself a safe, observable state, not a crash.

import os, sys, io
import M5
from M5 import *
import m5ui
import lvgl as lv
import network

ANIM_OFF = getattr(lv, "ANIM_OFF", 0)

page0 = None
title_label = None
dropdown0 = None
network_label = None
status_label = None

wlan = None

# Maps each dropdown option to its (ssid, password) pair. A real
# project would likely load this from a config file rather than
# hardcoding it -- kept simple here since the point of this example
# is the dropdown/connection-status pattern, not credential storage.
NETWORK_PROFILES = {
    "Home": ("home-network-ssid", "home-network-password"),
    "Office": ("office-network-ssid", "office-network-password"),
    "Mobile Hotspot": ("phone-hotspot-ssid", "phone-hotspot-password"),
}


def safe_connect(ssid, password):
    """Attempt to connect without ever letting the call crash the
    program. Disconnects first if already connected -- calling
    connect() while already connected, or while a prior attempt has
    not finished resolving, is exactly what triggers the confirmed
    "OSError: Wifi Internal State Error" on this hardware. The
    connect() call itself is also wrapped in try/except, since a
    disconnect() beforehand does not guarantee the radio's internal
    state machine is immediately ready for a new attempt.

    Returns True if the attempt was accepted (not yet necessarily
    connected -- connect() is non-blocking), False if rejected and
    safely ignored.
    """
    try:
        if wlan.isconnected():
            wlan.disconnect()
        wlan.connect(ssid, password)
        return True
    except OSError:
        return False


def dropdown0_changed(event_struct):
    selected = dropdown0.get_selected_str()
    network_label.set_text("Selected: %s" % selected)
    ssid, password = NETWORK_PROFILES[selected]
    accepted = safe_connect(ssid, password)
    if not accepted:
        # The attempt was rejected (most likely a previous connect()
        # was still resolving). Don't crash -- the status label's
        # existing loop()-driven check keeps reporting the true
        # connection state regardless.
        network_label.set_text("Selected: %s (retry)" % selected)


def dropdown0_handler(event_struct):
    if event_struct.code == lv.EVENT.VALUE_CHANGED:
        dropdown0_changed(event_struct)
    return


def setup():
    global page0, title_label, dropdown0, network_label, status_label, wlan

    M5.begin()
    Widgets.setRotation(1)
    m5ui.init()
    page0 = m5ui.M5Page(bg_c=0xFFFFFF)

    title_font = getattr(lv, "font_montserrat_20", lv.font_montserrat_14)
    title_label = m5ui.M5Label(
        "Network Selector", x=10, y=4,
        text_c=0x000000, bg_c=0xFFFFFF, bg_opa=0,
        font=title_font, parent=page0,
    )

    dropdown0 = m5ui.M5Dropdown(
        x=10, y=40, w=200, h=lv.SIZE_CONTENT,
        options=list(NETWORK_PROFILES.keys()),
        direction=lv.DIR.BOTTOM,
        show_selected=True,
        font=lv.font_montserrat_14,
        parent=page0,
    )
    dropdown0.add_event_cb(dropdown0_handler, lv.EVENT.ALL, None)

    network_label = m5ui.M5Label(
        "Selected: (none)", x=10, y=90,
        text_c=0x000000, bg_c=0xFFFFFF, bg_opa=0,
        font=lv.font_montserrat_14, parent=page0,
    )

    status_label = m5ui.M5Label(
        "Wi-Fi: Not Connected", x=10, y=120,
        text_c=0x000000, bg_c=0xFFFFFF, bg_opa=0,
        font=lv.font_montserrat_14, parent=page0,
    )

    wlan = network.WLAN(network.STA_IF)
    wlan.active(True)

    page0.screen_load()


def loop():
    M5.update()
    if wlan.isconnected():
        status_label.set_text("Wi-Fi: Connected")
    else:
        status_label.set_text("Wi-Fi: Not Connected")


if __name__ == '__main__':
    try:
        setup()
        while True:
            loop()
    except (Exception, KeyboardInterrupt) as e:
        try:
            m5ui.deinit()
            from utility import print_error_msg
            print_error_msg(e)
        except ImportError:
            print("please update to latest firmware")
```

### 7. Key Takeaways

- Wi-Fi is set up with `network.WLAN(network.STA_IF)` → `.active(True)`
  → `.connect(ssid, password)` — and, like `Mic.record()` and
  `Speaker.tone()`, `.connect()` does not block; the connection
  happens in the background.
- **`.isconnected()` is not a one-time check — it's a value that can
  change on its own, at any time, for reasons outside your program.**
  A connection status display belongs in `loop()`, checked fresh every
  pass, the same way every poll-driven sensor reading in this course
  has been.
- `M5Dropdown` fills the "choose one of several options, compactly,
  without free text" gap in the widget palette — configured with a
  fixed `options` list, read with `get_selected()` /
  `get_selected_str()`, and responded to with the same `VALUE_CHANGED`
  pattern every interactive widget in this course has used since
  Lecture 4.
- The options list isn't fixed forever — `set_options()`,
  `add_option()`, and `clear_options()` let a dropdown's choices be
  changed at runtime, which matters the moment a project needs to
  populate a dropdown from something discovered dynamically (like a
  Wi-Fi scan) rather than a list typed into the code.
- This lecture's worked example returns to the **poll-driven status +
  event-driven selection** shape from Lectures 4, 6, and 7 — a
  connection status that's re-checked every pass, paired with a
  dropdown selection that only changes on touch.
- **Confirmed on hardware: never call `wlan.connect()` unconditionally
  from an event handler.** Calling it again while a previous attempt
  is still resolving raises `OSError: Wifi Internal State Error`, and
  because this happens inside an event handler, it freezes the whole
  app rather than being silently absorbed. Guard every reconnect
  attempt with a `disconnect()`-if-connected step and a
  `try`/`except OSError`, exactly as `safe_connect()` does in the
  worked example above.
