# PRG455 — Agentic AI and Claude Code

**Week 9 reading · Read before starting Lab 8, and before starting the
Major Project in Weeks 10–11**

Every reading so far in this course has treated Claude as something
you have a **conversation** with: you write a precise prompt, it
writes back a function or a fix, you copy that into your file, you
test it on the CoreS3. That workflow doesn't disappear — it's still
exactly right for a single function, a one-line fix, or "what does
this error mean." But starting with Lab 8 and continuing through the
Major Project, some of your work is better handed to Claude as a
**task**, not a **question** — and that's a different way of working
with a different tool shape: **agentic AI**, used here through
**Claude Code**.

---

## 1. What "Agentic" Actually Means

The chat interface you've used since Week 1 — claude.ai in a browser,
or Claude Code answering one question — works like this: you provide
context, Claude produces text, you decide what to do with that text.
Every action in the loop after Claude's reply is yours: opening the
file, pasting the code, saving it, running it, checking the result.

An **agentic** tool changes what happens *after* Claude produces a
plan. Rather than handing you text to act on, it **acts directly** —
reading your actual files, writing changes to them, running commands,
checking whether those commands succeeded, and correcting course if
they didn't — for as long as the task takes, without you manually
relaying each step. Anthropic's own framing of this distinction is
worth stating plainly:

> Traditional AI coding tools suggest individual functions or code
> snippets based on immediate context, and you handle integration,
> testing, and making sure the result follows your project's
> conventions. Agentic coding tools instead understand your whole
> project, plan an approach, and execute the complete workflow
> themselves — reading files, making edits across several of them,
> running tests, and fixing what fails, with your review sitting at
> the checkpoints rather than between every keystroke.

This isn't a bigger autocomplete. It's Claude operating **inside your
repository** the way you would — opening files, editing them, running
your code, reading the error if something breaks, and trying again —
across a task that might touch one file or a dozen.

### Why this matters for this course specifically

Every lab so far has fit comfortably in the conversational shape: one
function, one widget, one clear specification. The **Major Project**
won't. It asks you to combine several hardware/widget pairings from
Weeks 3–9 into one application of your own design — multiple files,
multiple pieces of state interacting, a design that has to hold
together as a whole rather than as eight independent labs. That's
exactly the kind of work where relaying every single small edit by
hand through a chat window stops being the efficient way to work, and
where an agentic tool that can read your whole project, make a
coordinated set of changes, and verify them against your actual
hardware output starts to earn its keep.

## 2. You Already Have Claude Code — This Is About Using It Differently

Your Week 1 setup (`1.1_Claude_Pro_and_VS_Code.md`) already installed
Claude Code in VS Code and in your terminal, and you've been using it
since Lab 1 for the "prompt → review diff → accept → commit → push"
loop. That loop **is** agentic behavior at a small scale — Claude Code
read your file, proposed an edit, and you accepted it. What's new
starting this week isn't the tool. It's the **size and shape of the
task** you hand it, and a few habits that matter once a task grows
past "one function in one file."

---

## 3. Give It a Task, Not Just a Question

The four-part prompt pattern from Week 2
(`2_1_prompting_and_context.md` §5 — CONTEXT, TASK, CONSTRAINTS,
ACCEPTANCE) still applies, and still matters just as much here. What
changes is the **scope** of what you're asking for.

A conversational prompt asks for a piece:

```
Write a function that reads the spinbox's value and plays a tone.
```

An agentic task describes an outcome, across as much of the project
as it takes to get there:

```
CONTEXT: MicroPython on M5Stack Core S3, UIFlow2, M5UI widgets.
My repository has lab7/ (spinbox tone generator) and lab8/ (dropdown
network selector) as separate working programs.

TASK: Create a new project/ directory that combines both: a page with
the frequency spinbox and Play button from lab7, plus the network
dropdown and status label from lab8, on one screen.

CONSTRAINTS: Reuse the existing widget layout logic from both labs
rather than rewriting it from scratch. Follow the header block format
in CONTEXT.md. Keep the poll-driven Wi-Fi status check and the
event-driven Play button both working without either blocking the
other.

ACCEPTANCE: The combined app runs with Run Once, both the tone
generator and the network selector work independently on the same
screen, and the file follows this course's standard setup()/loop()
structure.
```

The second version asks Claude Code to look at two existing files,
figure out how to combine them, write the result, and tell you what it
did — a genuine multi-step task, not a single answer. This is the
shape of request agentic tools are built for.

---

## 4. Ask For a Plan Before Asking For Code

For anything touching more than one file, or anything you'd be upset
to have to undo, ask Claude Code to **plan first, edit second**. Two
ways to do this:

**Ask explicitly, in the prompt itself:**

```
Before making any changes, tell me your plan: which files you'll
touch, what you'll change in each, and in what order. Wait for me to
say "go" before editing anything.
```

**Use Plan Mode**, a built-in Claude Code mode for exactly this. In
Plan Mode, Claude Code can read files and run read-only commands to
investigate the codebase, but it **cannot edit anything** until you
approve the plan it proposes. In the VS Code extension and the
terminal, cycle to Plan Mode with `Shift+Tab`. This is the safest way
to let Claude Code explore a task's full scope — "what would need to
change to add a settings page" — without any risk of it changing
something before you've seen the shape of the answer.

**Reviewing a plan is not optional overhead — it's the entire value
of asking for one.** A plan that lists "modify `main.py`,
`network_setup.py`, and `PROMPTS.md`" tells you the blast radius of a
change before it happens. If that blast radius is bigger than you
expected, that's the moment to say so — not after the edits are
already made.

---

## 5. Review Diffs Like You Already Do — Just More of Them

Your Week 1 sign-off checklist already required looking at a diff
before accepting it. That habit does not change; it becomes **more
important**, because an agentic task can produce changes across
several files in one pass instead of one small edit.

- **Read every file Claude Code touched, not just the one you were
  thinking about.** A task that says "add Wi-Fi status to the main
  screen" might reasonably also touch a shared constants file or a
  layout helper — that's not necessarily wrong, but you need to see it
  to judge that.
- **A large diff is a signal to slow down, not a signal to trust it
  more because it looks thorough.** If a task you expected to touch
  one file touched six, ask why before accepting.
- **Test on the physical CoreS3 before committing**, exactly as this
  course has required since Lab 1. An agentic tool can tell you its
  code ran without a Python exception; it cannot tell you the LED
  actually lit up, the tone actually played, or the touch target is
  actually reachable with your thumb. That confirmation is still
  yours to do, on real hardware, every time.

## 6. `CONTEXT.md` Matters Even More Here

Week 2 introduced `CONTEXT.md` as the place for constraints that apply
to everything you write. For agentic tasks, this file does double
duty: Claude Code reads files in your project directory as part of
doing its job, and a `CONTEXT.md` sitting at the root of your
repository is exactly the kind of file it will naturally pick up and
apply — the same way it would notice your existing lab files follow a
particular header format and continue that pattern without being told
each time.

Keep it current as your project grows. If your Major Project settles
on a particular file layout, a particular widget-naming convention, or
a particular error-handling pattern partway through, update
`CONTEXT.md` to say so. An agentic tool asked to add a ninth file to
your project works better when the conventions of the first eight are
written down somewhere it will read them, rather than left for it to
infer — or worse, left for it to guess wrong and quietly diverge from.

---

## 7. Keep Tasks Scoped — "One Goal, Reviewable Diff"

The efficiency argument from Week 2 (precise prompts save allowance
because vague ones cost correction rounds) has a direct parallel here:
**a task with one clear goal produces a diff you can actually review;
a task with five goals produces a sprawl you can't.**

Prefer:

```
Add a "Status: Ready/Playing" label to the tone generator screen,
driven by Speaker.isPlaying() in loop(). Don't touch anything else.
```

over:

```
Improve the tone generator -- add a status label, clean up the
layout, make the code more efficient, and add error handling.
```

The second version isn't wrong to eventually want, but as a single
task it invites a diff that's hard to review, harder to test as a
whole, and hardest to un-do cleanly if one part of it turns out to be
wrong. Break it into four separate, reviewable tasks instead. This is
the same "one goal per change, reviewable diffs" discipline any
professional engineering team applies to agentic tools, not a
PRG455-specific rule.

## 8. What Doesn't Change

Everything Weeks 1–8 already established about working with Claude in
this course still holds, without exception, when the tool is acting
agentically instead of conversationally:

- **`PROMPTS.md` still applies.** Document what you asked Claude Code
  to do and what you kept from its output, the same as any other AI
  assistance this term — an agentic task is still AI assistance.
- **Physical hardware is still the ground truth.** Claude Code
  succeeding at "the code ran with no exception" is not the same as
  "the LED brightness actually tracks the microphone correctly on my
  device." Test on the CoreS3, every time, exactly as this course has
  required since Lab 2.
- **`Run Once`, never `Run Always`, until you've verified the code
  works.** This rule doesn't relax just because an agentic tool wrote
  the code instead of you typing it.
- **Your allowance is still shared and still finite.** Agentic tasks
  that read and re-read files across a multi-step task can consume
  your Pro allowance faster than a short conversational exchange,
  since more file content moves through context per task. Check
  `/status` before starting a substantial agentic task, the same
  habit Week 1 already asked you to build.
- **You are still responsible for the result.** An agentic tool
  choosing *how* to implement something doesn't change that you
  decided *what* to build and are the one who must verify it actually
  works. Domain understanding — knowing what "correct" looks like on
  this specific hardware — is what makes agentic assistance useful
  rather than merely fast.
