### 1. The Widget Palette So Far

Six of the course's nine approved widgets have been covered. Two
things are worth noticing about the list as a whole before drilling
into each one: every widget you construct takes `parent=page0` (or
whatever page it belongs to), and every widget that responds to touch
uses the exact same `add_event_cb` / dispatch-on-`event_struct.code`
shape — there is only one event pattern in this course, not six.

| Widget | Introduced | Update pattern | Key method(s) |
|---|---|---|---|
| `M5Label` | Week 3 | Either — usually event-driven | `set_text()` |
| `M5Button` | Week 3 | Event-driven only | `add_event_cb`, dispatch on `lv.EVENT.CLICKED` |
| `M5Slider` | Week 3 | Event-driven | `get_value()`, `set_value(v, ANIM_OFF)`, dispatch on `lv.EVENT.VALUE_CHANGED` |
| `M5Bar` | Week 4 | **Poll-driven only** | `set_value(v, ANIM_OFF)` — no `add_event_cb`, no `get_value()` |
| `M5Switch` | Week 4 | Event-driven | `get_state()`, `set_state(bool, ANIM_OFF)`, dispatch on `lv.EVENT.VALUE_CHANGED` |
| `M5Image` | Week 5 | Neither — set once, updated by explicit calls | `set_image(path)`, `set_pos()`, `set_rotation()`, `set_scale()` |

Three widgets remain for later weeks — `M5LED` (Week 7), `M5Spinbox`
(Week 8), `M5Dropdown` (Week 9) — none of which are in scope for Lab
Test 1.

### 2. Poll-Driven vs. Event-Driven — the Question Every Spec Asks

Every functional requirement you've built this term reduces to one of
two shapes:

**Poll-driven:** something is read fresh, every single pass through
`loop()`, whether or not the user touched anything. This is how you
show a live sensor value — the IMU readings in Week 4, the camera
frames in Week 5. `M5Bar` is the one widget that is **only** ever
updated this way; it has no event of its own.

```python
def loop():
    M5.update()
    ax, ay, az = M5.Imu.getAccel()
    tilt_bar.set_value(scale(ax), ANIM_OFF)
```

**Event-driven:** something runs exactly once, in response to a
specific user action — a button press, a slider drag, a switch
flip — and does nothing the rest of the time. This is every button
handler you've written, and it's the *only* way `M5Switch` and
`M5Slider` update their own downstream logic.

```python
def capture_button_clicked(event_struct):
    # runs once, only when the button is actually pressed
    ...

def capture_button_handler(event_struct):
    if event_struct.code == lv.EVENT.CLICKED:
        capture_button_clicked(event_struct)
    return
```

**The most common mistake under time pressure** is picking the wrong
one for a given requirement — writing a live sensor read inside a
button handler (so it only updates once per press instead of
continuously), or writing continuous polling logic for something that
should only happen once (so it fires 30+ times a second instead of
once per touch). When you read a spec, the first thing to identify for
each requirement is: **does this update on its own, or only in
response to a specific action?** That answer tells you where the code
belongs before you write a single line.

Some programs need both patterns at once — Lab 4 combined a
continuously-polled bar with an event-driven switch in the same
`loop()`. Nothing about combining them is special; they're just two
independent things happening inside the same `while True:`, each doing
its own job.

### 3. Five Gotchas Worth Having Memorized

These aren't things to look up during the test — by now they should be
automatic. Each one has bitten a real, working-looking program in a
previous week.

**1. `M5Label` has no `w`/`h`.** It draws at `(x, y)` and grows to fit
with nothing clipping it. Any label that might display a long or
variable-length string needs its longest-case length worked out and
its `y` position chosen with room to spare — *before* you place it, not
after it clips off the bottom edge. (Week 3)

**2. Font sizes other than 14 must be looked up defensively.**
`lv.font_montserrat_14` is always present; anything else might not be,
depending on the firmware build. Always:

```python
title_font = getattr(lv, "font_montserrat_20", lv.font_montserrat_14)
```

Using an unavailable size directly is an `AttributeError` at
widget-creation time, not a warning. (Week 3)

**3. `set_value()` on a slider or bar takes two arguments, not one.**
Value, then an animate flag:

```python
some_slider.set_value(0, lv.ANIM.OFF)   # or getattr(lv, "ANIM_OFF", 0)
```

Leaving out the second argument is a `TypeError`. This applies
consistently across the widget set — sliders, bars, switches all take
this same two-argument shape when set programmatically. (Week 3)

**4. `M5Switch.get_state()` lags one step behind on the off-transition.**
This is a confirmed CoreS3/LVGL hardware quirk, not a coding mistake —
reading `get_state()` inside the switch's own handler can report the
*previous* state on the transition back to off. The reliable fix is a
boolean flip as the single source of truth:

```python
sensitive_mode = False

def calibration_switch_toggled(event_struct):
    global sensitive_mode
    sensitive_mode = not sensitive_mode
    # use sensitive_mode from here on -- not get_state()
```

`get_state()` is safe to use for a one-time read (e.g. checking the
switch's position in `setup()`), just not as the running source of
truth inside its own change handler. (Week 4)

**5. `M5Image` must be constructed with a path that already exists,
and only ever accepts file paths — never a live frame or raw bytes.**
This is why a captured photo has to be written to flash and then
loaded with `set_image()`, rather than handed to the widget directly.
Constructing `M5Image` against a nonexistent path is a crash at
widget-creation time, exactly like the font gotcha above — not a safe
no-op that renders blank and waits. (Week 5)

### 4. Reading an Unfamiliar Spec Under Time Pressure

Lab Test 1 will describe a scenario you haven't built before, using
widgets you already know. The skill being tested isn't "have you
memorized this exact program" — it's "can you decompose a new spec
into the same small set of patterns you've already used four times."

A reliable way to read any spec in this course, including the test:

1. **List every widget the spec implies**, even if it doesn't name
   them outright — "the user picks one of four options" is a slider or
   a switch, not free text; "show a running count" is a label updated
   from `loop()` or from a handler, depending on what's counting.
2. **For each widget, decide poll-driven or event-driven** using the
   test from §2 — does it update on its own, or only in response to a
   specific action?
3. **Identify any formula or decision logic explicitly**, and work
   out at least one hand-checkable example before writing code — the
   same worked-check habit every lab's Decision Logic section has
   modeled for you.
4. **Sketch rough coordinates before placing widgets**, accounting for
   the two overlap traps you've already hit: labels with no fixed box
   (§3.1) and any full-screen live-drawing region ignoring M5UI's
   widget stacking entirely (Week 5, `M5.Lcd.show()`).
5. **Test on the physical device early**, not just at the end. A
   program that "looks right" in the editor can still fail for
   firmware-specific reasons no amount of re-reading the code will
   surface — the `get_state()` lag and the missing-font crash were
   both found this way, not by inspection.

### 5. Key Takeaways

- Six widgets, one event pattern (`add_event_cb` + dispatch on
  `event_struct.code`), two update patterns (poll-driven in `loop()`,
  event-driven in a handler). Every requirement you'll see reduces to
  picking the right widget and the right pattern for it.
- `M5Bar` is poll-only; `M5Button` is event-only; `M5Slider` and
  `M5Switch` are event-driven with a readable current state;
  `M5Label` and `M5Image` are updated by explicit calls whenever your
  own logic decides to.
- The five gotchas in §3 are the specific, confirmed ways working-
  looking code fails on this hardware. Know them going in — the test
  won't re-explain them.
- Decomposing an unfamiliar spec into widgets + update pattern +
  layout, before writing any code, is the actual skill being graded.
