### 1. What the IMU Actually Is

IMU stands for **Inertial Measurement Unit**. The CoreS3's IMU is a
6-axis sensor: a 3-axis **accelerometer** (how much force is being
applied along each axis, including gravity) and a 3-axis **gyroscope**
(how fast the device is rotating around each axis). This course uses
only the accelerometer — it's simpler to reason about, and it's enough
to build everything Lab 4 asks for.

You already used it once, in Lab 2's stretch activity:

```python
ax, ay, az = M5.Imu.getAccel()
```

`ax`, `ay`, and `az` are floating-point values, roughly in units of
**g** (Earth's gravity, ≈ 9.8 m/s²). Flat on a table, screen up, `az`
reads close to **1.0** and `ax`/`ay` read close to **0.0** — gravity is
pulling straight down through the axis pointing into the table. Tilt
the device and gravity's pull redistributes across the three axes.
That's the entire physical principle behind everything in this
lecture and in Lab 4: **tilt changes which axis gravity loads onto,
and by how much.**

### 2. From Raw Axis to a Bounded Display Value

A raw accelerometer axis is a small floating-point number roughly
between -1.0 and 1.0 (a bit beyond that under sudden motion — this
course ignores that case). An `M5Bar` widget, like a slider, wants an
**integer inside a fixed `min_value`/`max_value` range**. Getting from
one to the other is a single **clamp-and-scale** step, and it's a
pattern you'll reuse constantly with sensor-driven widgets:

```python
def clamp(value, low, high):
    if value < low:
        return low
    if value > high:
        return high
    return value

def accel_to_bar(ax, low_g=-1.0, high_g=1.0, bar_min=0, bar_max=100):
    ax = clamp(ax, low_g, high_g)
    fraction = (ax - low_g) / (high_g - low_g)   # 0.0 .. 1.0
    return int(bar_min + fraction * (bar_max - bar_min))
```

Two things worth noticing:

- **`clamp()` runs first.** Without it, a harder tilt or a bump can
  push the raw value outside ±1.0 g, and the scaled result would fall
  outside the bar's range — which `M5Bar` will not politely clip for
  you.
- **The scale is linear**, the same shape as the VRAM formula from
  Lab 3 — a raw input mapped through a fixed formula to one
  unambiguous, gradable output. This is a pattern, not a coincidence:
  event-driven embedded code is mostly this shape, over and over,
  with different sensors and different formulas.

### 3. `M5Bar` — showing a live, continuously-changing value

An `M5Bar` looks like a slider but the user can't drag it — it's
**read-only display**, driven entirely from code. That makes it the
right widget any time you want to *show* a sensor value rather than
*collect* a user choice.

```python
tilt_bar = m5ui.M5Bar(
    x=10, y=50, w=300, h=18,
    min_value=0, max_value=100, value=50,
    bg_c=0x115E9F, color=0x2C90E4,
    parent=page0,
)
```

Notice the constructor arguments are almost identical to `M5Slider` —
same `min_value`/`max_value`/`value`, same `bg_c`/`color` styling. The
difference is behavioural, not structural: nothing in the widget
itself responds to touch.

Updating it takes **two** arguments, exactly like a slider — a value
and an animate flag:

```python
tilt_bar.set_value(new_value, ANIM_OFF)
```

Because there's no user interaction to catch, `M5Bar` has **no
`VALUE_CHANGED` event** and needs **no `add_event_cb` registration at
all**. You drive it directly from `loop()`, on your own schedule:

```python
def loop():
    M5.update()
    ax, ay, az = M5.Imu.getAccel()
    tilt_bar.set_value(accel_to_bar(ax), ANIM_OFF)
```

This is the first widget in the course that's updated from `loop()`
instead of from an event callback — a genuinely new pattern, and the
one Lab 4 leans on hardest.

### 4. `M5Switch` — a two-state toggle

`M5Switch` is what you reach for any time the program needs a clean
**on/off** or **A/B** state that the user sets directly, rather than a
value picked from a range. Its API mirrors `M5Button` and `M5Slider`:
build it, register a handler, and dispatch on the event code.

```python
mode_switch = m5ui.M5Switch(
    x=10, y=90, w=50, h=25,
    parent=page0,
)

def mode_switch_changed(event_struct):
    if mode_switch.get_state():
        mode_label.set_text("Mode: Calibrated")
    else:
        mode_label.set_text("Mode: Raw")

def mode_switch_handler(event_struct):
    if event_struct.code == lv.EVENT.VALUE_CHANGED:
        mode_switch_changed(event_struct)
    return

mode_switch.add_event_cb(mode_switch_handler, lv.EVENT.ALL, None)
```

`mode_switch.get_state()` returns `True`/`False` (on/off). Setting it
programmatically — for a reset, or to force a starting state — takes
a boolean and, like the bar and slider, an animate flag:

```python
mode_switch.set_state(False, ANIM_OFF)
```

The event-callback shape is identical to everything you already know
from Lecture 3 — one handler, registered with `add_event_cb`,
dispatching on `event_struct.code`. What's new is only the widget
itself and what its two states mean for your program.

### 5. Two Update Patterns, One Program

Lecture 3's labs updated widgets **only** in response to events — a
slider drag, a button press. Lecture 4 introduces a second pattern
that runs **continuously, every pass through `loop()`**, independent
of any touch event at all:

| Pattern | Driven by | Example |
|---|---|---|
| Event-driven | A `VALUE_CHANGED` or `CLICKED` event fires | `M5Switch` toggled, `M5Button` pressed |
| Poll-driven | `loop()` runs, every iteration, no event needed | `M5.Imu.getAccel()` read, `M5Bar` updated |

Both patterns coexist in the same program without conflict — the
switch's handler only runs when the user touches it, while the bar
update runs on every single pass through `loop()`, dozens of times a
second, whether or not anything else happened. Lab 4 requires exactly
this combination: a bar that update continuously from the IMU, and a
switch whose handler fires only when touched.

One consequence worth planning for: **because the bar updates on every
loop iteration, its own code must be cheap.** Don't do anything slow
or blocking inside `loop()` — no `time.sleep()` longer than a few
milliseconds, no network calls — or the whole UI stalls, including
touch response on the switch.

### 6. Worked Example — Tilt Monitor

This ties every idea in this lecture together: a bar that continuously
reflects the device's tilt, and a switch that changes *how* the raw
accelerometer value is interpreted before it reaches the bar. It's the
same overall shape Lab 4 asks for — a live sensor-driven bar, a
mode-changing switch — applied to a slightly different scenario.

```python
# SPDX-License-Identifier: MIT
#
# PRG455 Lecture 4 -- Tilt Monitor
# Demonstrates M5Bar (continuously updated from the IMU in loop()) and
# M5Switch (an event-driven mode toggle), and the clamp-and-scale
# pattern for turning a raw accelerometer axis into a bar-friendly
# integer.

import os, sys, io
import M5
from M5 import *
import m5ui
import lvgl as lv

ANIM_OFF = getattr(lv, "ANIM_OFF", 0)

page0 = None
title_label = None
tilt_bar = None
value_label = None
mode_switch = None
mode_label = None

SENSITIVE_RANGE = 0.5   # +/- g considered full-scale in Sensitive mode
NORMAL_RANGE = 1.0      # +/- g considered full-scale in Normal mode


def clamp(value, low, high):
    if value < low:
        return low
    if value > high:
        return high
    return value


def accel_to_bar(ax, half_range):
    ax = clamp(ax, -half_range, half_range)
    fraction = (ax + half_range) / (2 * half_range)
    return int(fraction * 100)


def mode_switch_changed(event_struct):
    if mode_switch.get_state():
        mode_label.set_text("Mode: Sensitive")
    else:
        mode_label.set_text("Mode: Normal")


def mode_switch_handler(event_struct):
    if event_struct.code == lv.EVENT.VALUE_CHANGED:
        mode_switch_changed(event_struct)
    return


def setup():
    global page0, title_label, tilt_bar, value_label
    global mode_switch, mode_label

    M5.begin()
    Widgets.setRotation(1)
    m5ui.init()
    page0 = m5ui.M5Page(bg_c=0xFFFFFF)

    title_font = getattr(lv, "font_montserrat_20", lv.font_montserrat_14)
    title_label = m5ui.M5Label(
        "Tilt Monitor", x=10, y=4,
        text_c=0x000000, bg_c=0xFFFFFF, bg_opa=0,
        font=title_font, parent=page0,
    )

    tilt_bar = m5ui.M5Bar(
        x=10, y=50, w=300, h=18,
        min_value=0, max_value=100, value=50,
        bg_c=0x115E9F, color=0x2C90E4, parent=page0,
    )

    value_label = m5ui.M5Label(
        "X-axis: 0.000 g", x=10, y=76,
        text_c=0x000000, bg_c=0xFFFFFF, bg_opa=0,
        font=lv.font_montserrat_14, parent=page0,
    )

    mode_label = m5ui.M5Label(
        "Mode: Normal", x=10, y=110,
        text_c=0x000000, bg_c=0xFFFFFF, bg_opa=0,
        font=lv.font_montserrat_14, parent=page0,
    )
    mode_switch = m5ui.M5Switch(
        x=10, y=132, w=50, h=25,
        parent=page0,
    )
    mode_switch.add_event_cb(mode_switch_handler, lv.EVENT.ALL, None)

    page0.screen_load()


def loop():
    M5.update()
    ax, ay, az = M5.Imu.getAccel()

    half_range = SENSITIVE_RANGE if mode_switch.get_state() else NORMAL_RANGE
    tilt_bar.set_value(accel_to_bar(ax, half_range), ANIM_OFF)
    value_label.set_text("X-axis: %.3f g" % ax)


if __name__ == '__main__':
    try:
        setup()
        while True:
            loop()
    except (Exception, KeyboardInterrupt) as e:
        try:
            m5ui.deinit()
            from utility import print_error_msg
            print_error_msg(e)
        except ImportError:
            print("please update to latest firmware")
```

Notice that `value_label` is updated from `loop()` too, right next to
the bar — any label showing a live sensor reading follows the bar's
poll-driven pattern, not the slider's event-driven one, even though
`M5Label.set_text()` is the same call you've used since Lecture 3.

### 7. Key Takeaways

- `M5.Imu.getAccel()` returns `(ax, ay, az)` in roughly ±1.0 g; flat
  on a table, one axis reads near 1.0 and the other two read near 0.0.
- **Clamp before you scale.** A raw axis can exceed your chosen range
  under a hard tilt or bump; without `clamp()`, a scaled value can
  land outside a bar's `min_value`/`max_value`.
- `M5Bar` looks like a slider but is **read-only** — no touch
  interaction, no `VALUE_CHANGED` event, no `add_event_cb`. You update
  it directly, from `loop()`, with `set_value(value, ANIM_OFF)`.
- `M5Switch` follows the same build/handler/dispatch shape as every
  other interactive widget so far: `add_event_cb`, dispatch on
  `event_struct.code == lv.EVENT.VALUE_CHANGED`, read state with
  `get_state()`, set it with `set_state(bool, ANIM_OFF)`.
- This lecture's programs mix **two update patterns** in one
  `setup()`/`loop()` program for the first time: event-driven
  (switch) and poll-driven (bar, IMU). Keep whatever runs inside
  `loop()` cheap — it runs every single iteration, whether or not the
  user touched anything.
